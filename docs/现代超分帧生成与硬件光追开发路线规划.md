# Mecraft 现代超分、帧生成与硬件光追开发路线规划

> 编制日期：2026-07-14
>
> 目标显卡：NVIDIA GeForce RTX 4060 Laptop GPU，8GB 显存
>
> 当前主要开发平台：Arch Linux
>
> 目标图形后端：Vulkan 1.3

## 1. 文档目的

Mecraft 已完成面向现代显式图形 API 的 RHI，并实现 OpenGL 与 Vulkan 后端。RHI 的公共模型以 Vulkan、Direct3D 12 等现代 API 的资源、管线、命令和同步方式为设计基准，OpenGL 后端负责适配该模型。

下一阶段的目标是基于 Vulkan 后端加入以下能力：

- AMD FidelityFX Super Resolution 3.1 时域超分。
- NVIDIA DLSS Super Resolution。
- NVIDIA DLSS Frame Generation 2x。
- NVIDIA Reflex Low Latency 与 PCL 标记。
- AMD FidelityFX Super Resolution 3.1 Frame Generation。
- Vulkan KHR 加速结构与 Ray Query。
- RTX 4060 Laptop GPU 上的硬件加速光追效果。
- 在确有复杂光追着色需求时加入完整 Ray Tracing Pipeline。

本规划不包含 RTX 50 系专属的 Multi Frame Generation，也不以增加 Direct3D 12 后端作为上述功能的前置条件。

## 2. 固定架构原则

### 2.1 RHI 边界

- 公共 RHI 不出现 `VkImage`、`VkImageView`、`VkCommandBuffer`、`VkDevice` 等 Vulkan 类型。
- 第三方 SDK 所需的原生对象由 Vulkan 后端私有 interop 接口提供。
- OpenGL 后端维持现有功能边界，新的时域超分、帧生成和硬件光追功能只在 Vulkan 路径实现。
- 功能选择由设置明确指定。设备、系统、驱动或 SDK 条件不满足时，功能保持关闭并返回明确原因。
- 初始化和运行时错误使用错误码或 `std::optional` 表达，不使用异常捕获。

### 2.2 技术组合

- 每帧只启用一种时域重建方案。
- 每个交换链只启用一种帧生成方案。
- 时域超分启用时，独立 TAA resolve 不参与同一帧。
- 帧生成不作为普通 render pass，它属于展示与交换链控制层。
- UI 与 HUD-less scene 必须形成独立资源契约。
- 光追能力按 Ray Query 和完整 Ray Tracing Pipeline 两个阶段建设。

### 3.3 当前主要缺口

| 模块 | 当前状态 | 目标状态 |
| --- | --- | --- |
| 分辨率模型 | `frameWidth/frameHeight` 与 FSR1 比例 | 独立 `renderExtent/outputExtent` |

| Vulkan SDK interop | 未建立 | 受控的 Vulkan 原生对象访问接口 |
| 光追 | 只有 capability 字段 | AS、Ray Query、build command 与场景管理 |

## 5. 阶段一：统一时域重建帧契约

这是所有 SDK 接入之前必须完成的阶段。

### 5.1 设置模型

将当前 `UpscaleSettings` 改造为明确的技术和质量配置：

```cpp
enum class TemporalUpscalerType {
    Native,
    Fsr31,
    Dlss
};

enum class TemporalUpscaleQuality {
    Native,
    Quality,
    Balanced,
    Performance,
    UltraPerformance
};
```

设置结构至少包含：

- upscaler type。
- quality mode。
- output width 和 output height。
- sharpening enable 与 strength。
- dynamic resolution enable。
- debug visualization enable。

渲染尺寸必须由选中的时域技术根据 output extent 查询。业务渲染层不保存各厂商的固定缩放比例表。

### 5.2 帧输入结构

新增统一结构表达：

- render extent。
- output extent。
- jitter pixels。
- jitter projection offset。
- motion-vector scale。
- frame delta milliseconds。
- pre-exposure。
- camera near/far。
- vertical FOV radians。
- reset 标记。
- HDR color、depth、velocity、exposure、reactive mask 和 transparency mask。
- output HDR texture。

### 5.3 Motion vector 契约

当前 Mecraft velocity buffer 存储：

```text
currentTextureUv - previousTextureUv
```

公共帧契约必须固定记录该方向、坐标域、Y 轴方向和数值范围。FSR 与 DLSS bridge 负责执行一次确定的符号和缩放变换。禁止不同 pass 各自解释 velocity 方向。

所有可见运动对象应写入速度：

- terrain 和 block entities。
- humanoid entities。
- falling blocks。
- drops。
- first-person held item。
- particles 与 precipitation 中适合提供运动信息的部分。
- alpha-tested 与 alpha-blended geometry。

### 5.4 Reactive mask

新增 `R8Unorm` reactive mask，主要写入：

- 水面。
- 半透明方块。
- 粒子。
- 雨雪。
- 火焰与 emissive animation。
- 快速变化的程序化材质。

Reactive mask 数值来自实际 alpha、发光变化和材质语义，不由 CPU 对画面内容进行猜测。

### 5.5 Transparency and composition mask

新增 `R8Unorm` transparency/composition mask，主要标记：

- screen-space reflection。
- ray-traced reflection。
- 动画纹理。
- 特殊合成区域。
- 无法由常规 depth/velocity 完整描述的着色变化。

### 5.6 Camera reset

下列事件设置 temporal reset：

- 传送。
- 世界加载与卸载。
- 相机实体切换。
- 第一人称与特殊观察模式发生不连续切换。
- render extent 或 output extent 改变。
- upscaler type 或 quality 改变。
- FOV、near plane 或 far plane 发生不连续变化。
- shader reload 改变时域输入语义。

### 5.7 后处理顺序

时域超分输入保持 HDR。以下操作安排在超分之后：

- tonemap。
- film grain。
- vignette。
- display-space sharpen。
- UI。
- debug dashboard。

Bloom、景深、运动模糊等效果根据实际采样成本与画质评估决定运行分辨率，并通过 Render Graph 显式表达位置。

### 5.8 最小可执行 Render Graph

第一版 Render Graph 需要实现：

- imported texture/buffer。
- transient texture/buffer。
- graphics、compute、copy 和 external SDK pass。
- pass 资源读写声明。
- 资源状态推导。
- texture/buffer barrier 生成。
- queue dependency 生成。
- pass debug name 与 GPU timestamp。
- 每帧集中提交。

第一版不加入复杂的 transient memory aliasing。

### 5.9 验收标准

- Native 模式画面与当前 Vulkan deferred pipeline 一致。
- 不同 render/output extent 能稳定 resize。
- velocity debug view 能验证方向、动态物体和天空运动。
- camera reset 后首帧不读取旧 history。
- reactive/transparency mask 具备独立 debug view。
- Render Graph 在 Vulkan validation layer 下无 barrier、layout 和同步错误。

## 6. 阶段二：FSR 3.1 Upscaling

### 6.1 SDK 版本

Vulkan 路径固定使用 FidelityFX SDK `v1.1.4` 中的 FSR 3.1.4 API。

AMD 当前 FidelityFX SDK `v2.3.0` 主线在官方已知问题中标注 Vulkan 暂不受 SDK 支持，因此本项目不采用该主线完成 Vulkan FSR 3.1 集成。

### 6.2 Vulkan interop

在 `src/renderer/rhi/vulkan/` 内建立私有 interop 接口，提供：

- `VkInstance`。
- `VkPhysicalDevice`。
- `VkDevice`。
- graphics/compute queue 与 family index。
- `RhiTextureHandle` 对应的 `VkImage`、`VkImageView`、format 和 extent。
- `RhiCommandList` 对应的 `VkCommandBuffer`。
- RHI resource state 与 Vulkan layout/access/stage 映射信息。

interop 对象只服务 Vulkan 专用 bridge 和 SDK 集成层。

### 6.3 集成顺序

1. 创建 FSR 3.1 Vulkan backend context。
2. 根据 quality mode 查询 render extent。
3. 使用 FSR jitter phase count 与 jitter offset。
4. 注册 HDR color、depth、velocity、exposure 和 masks。
5. 创建 output-resolution HDR texture。
6. 在 Render Graph external pass 中 dispatch FSR。
7. 将输出交给高分辨率后处理。
8. 加入 SDK debug checker 和 debug view。

### 6.4 验收标准

- Quality、Balanced、Performance 三种模式稳定运行。
- 动态物体边缘无明显拖影。
- 水面、粒子、雨雪和 emissive animation 的 reactive mask 有效。
- resize、全屏切换、世界切换和相机传送行为正确。
- FSR debug checker 不报告输入契约错误。
- GPU capture 中 dispatch 输入输出和资源状态正确。
- 与 Native TAA 对比时记录 GPU 帧时间、显存占用和画质截图。

## 7. 阶段三：展示控制器与独立 UI

### 7.1 PresentationController

新增展示控制器，统一管理：

- frame acquire。
- HUD-less color。
- UI color/alpha texture。
- Native Present。
- FSR Frame Generation present。
- DLSS Frame Generation present。
- resize、最小化、全屏和 VSync 状态变化。
- 真实帧编号与展示帧统计。
- frame pacing 与展示错误状态。

`GameFrameOrchestrator` 不再直接固定执行“UI 写入 swapchain 后 present”的流程，而是把 scene 和 UI 资源交给展示控制器。

### 7.2 UI 资源

UI 渲染目标改为 output-resolution RGBA texture：

- RGB 保存 UI color。
- A 保存 UI coverage。
- 支持 premultiplied alpha。
- 至少双缓冲。
- dashboard 与常规 HUD 使用同一展示契约。

展示控制器负责将 UI 合成到真实帧和生成帧。

### 7.3 验收标准

- Native Present 下独立 UI 与当前画面一致。
- UI texture alpha 和颜色空间正确。
- UI 资源在异步展示期间不被提前复用。
- resize 和窗口状态变化不会访问已销毁的展示资源。
- present 统计能区分真实帧与生成帧。

## 8. 阶段四：Windows Streamline、DLSS SR 与 DLSS-G

### 8.1 平台要求

DLSS 与 DLSS Frame Generation 的正式开发和验证转到 Windows：

- Windows 10 2004 或更高版本。
- Hardware-accelerated GPU Scheduling 开启。
- NVIDIA 官方建议驱动版本。
- Streamline 官方 release 中的签名 DLL。
- Vulkan 1.2 以上，本项目继续使用 Vulkan 1.3。

RTX 4060 Laptop 使用 DLSS Frame Generation 2x，即每个真实帧生成一个插值帧。

### 8.2 Vulkan feature requirement negotiation

当前 Vulkan 后端使用固定设备扩展列表。Streamline 接入前建立 Vulkan requirement collector，在实例和设备创建之前汇总：

- RHI 基础扩展和 feature。
- Streamline 请求的 instance/device extensions。
- Streamline 请求的 Vulkan 1.2/1.3 feature chain。
- Streamline 请求的 graphics/compute queue 数量。
- Ray Query 与后续 RT Pipeline 请求的扩展和 feature。
- debug utils。

最终只创建一套经过验证的 Vulkan instance/device 配置。

### 8.3 DLSS Super Resolution

集成内容：

- `slInit` 在 Vulkan API 调用之前执行。
- Vulkan instance/device 创建完成后提供 `sl::VulkanInfo`。
- 查询 DLSS support 和 optimal settings。
- tag HDR input、depth、motion vectors、exposure 和 output。
- 提供 non-jittered camera matrices。
- 提供 pixel-space jitter。
- 提供 motion-vector scale。
- 在 Render Graph external pass 中执行 DLSS evaluate。

DLSS SR 与 FSR 3.1 使用同一份高层 temporal input contract。

### 8.4 Reflex 与 PCL

在 DLSS-G 之前完成：

- simulation start/end markers。
- render submit start/end markers。
- present start/end markers。
- input sample marker。
- `slReflexSleep` 调用位置。
- Off、On、On + Boost 设置。
- PCL latency report。

frame index 必须与 Streamline common constants 和实际 present 完全一致。

### 8.5 DLSS Frame Generation

DLSS-G 输入包括：

- depth。
- motion vectors。
- HUD-less color。
- UI color/alpha。
- common camera constants。
- 与 present 对齐的 frame token。

集成还需要：

- Streamline Vulkan acquire/present interception 或 manual hooking。
- input resource 生命周期同步。
- binary semaphore acquire/present 契约。
- DLSS-G 启停时的交换链生命周期管理。
- loading、暂停、菜单和窗口操作期间明确关闭 frame generation。
- motion blur 强度与生成帧模式联动。

### 8.6 验收标准

- DLSS Quality、Balanced、Performance 稳定运行。
- DLSS-G 2x 在 RTX 4060 Laptop 上可用。
- Reflex Verification HUD 中 marker 和 duration 有效。
- FrameView 的 display-change pacing 稳定。
- UI 在真实帧和生成帧上无插值扭曲。
- resize、最小化、全屏、VSync 与 frame generation 状态变化稳定。
- Streamline 日志无输入、同步和资源生命周期错误。

## 9. 阶段五：FSR 3.1 Frame Generation

FSR 3.1 Frame Generation 继续使用 FidelityFX SDK `v1.1.4` Vulkan API。

### 9.1 集成内容

- FSR frame interpolation context。
- FSR frame-generation swapchain context。
- optical flow 输入和工作资源。
- game motion vectors。
- depth。
- HUD-less color。
- UI texture composition。
- frame generation prepare dispatch。
- synchronous 与 asynchronous workload profiling。
- graphics/compute/present queue 同步。

### 9.2 UI 模式

本项目采用独立 UI texture，由 frame-generation swapchain 合成到真实帧和生成帧。UI texture 至少双缓冲，资源生命周期由 PresentationController 管理。

### 9.3 验收标准

- FSR 3.1 Frame Generation 在 Vulkan 路径稳定运行。
- RTX 4060 Laptop 上能正确生成中间帧。
- UI、半透明控件和 dashboard 无明显插值错误。
- 异步计算模式无 queue ownership 和资源生命周期错误。
- 真实帧率、展示帧率、GPU 时间和延迟分别统计。

## 10. 阶段六：Vulkan Ray Query RHI

### 10.1 Vulkan 扩展与 feature

启用并验证：

- `VK_KHR_acceleration_structure`。
- `VK_KHR_deferred_host_operations`。
- `VK_KHR_ray_query`。
- `VK_KHR_buffer_device_address`。
- acceleration structure feature chain。
- ray query feature chain。

### 10.2 公共 RHI 新增能力

新增：

- acceleration structure handle。
- BLAS/TLAS 描述结构。
- triangle geometry 和 AABB geometry 描述。
- build size query。
- scratch buffer 需求。
- acceleration structure descriptor binding。
- AS build input buffer usage。
- AS storage buffer usage。
- AS build、AS read 资源状态。
- build/update/copy/compact command。
- acceleration structure property query。

Ray Query 阶段不需要 RayGen、Miss、ClosestHit 和 SBT。

### 10.3 场景加速结构

#### Terrain

- 以 chunk section 或经过测量确定的 chunk group 作为 BLAS 单元。
- opaque 和 alpha-tested geometry 明确设置 geometry flags。
- chunk mesh 更新时重建对应 BLAS。
- 不可见且超出 RT 距离的 BLAS不进入当前 TLAS。
- 静态 BLAS 执行 compaction。

#### Dynamic objects

- humanoid、drop、falling block 和 block entity 使用独立 BLAS instance。
- 仅 transform 变化时更新 TLAS instance transform。
- 顶点拓扑变化时更新或重建 BLAS。

#### TLAS

- 每帧根据当前可见 RT instance 构建或更新。
- instance mask 区分 terrain、entity、transparent 和 emissive 类别。
- 与 raster frame 使用一致的世界坐标和 camera origin。

### 10.4 RTX 4060 Laptop 显存控制

必须记录：

- BLAS 原始大小。
- compacted BLAS 大小。
- TLAS 大小。
- scratch buffer 峰值。
- RT material/instance buffer 大小。
- FSR/DLSS 与 frame generation 的额外显存。
- 每帧 RT 工作集总量。

8GB 显存环境要求加速结构与 chunk streaming 共享明确预算，禁止无限保留远距离 BLAS。

### 10.5 第一个光追效果

第一个功能选择 Ray Query contact shadow 或单射线太阳阴影：

- 使用 deferred GBuffer depth 和 normal 重建世界位置。
- 每像素发射一条 shadow ray。
- 使用 blue-noise/jitter 采样软阴影。
- 使用 velocity、depth 和 normal 进行时域累积。
- 使用 spatial filter 完成降噪。
- 输出进入 deferred lighting。

该功能用于验证：

- BLAS/TLAS 几何正确性。
- alpha-tested geometry 处理。
- instance transform。
- ray origin bias。
- AS barrier 与生命周期。
- 时域降噪输入。

### 10.6 后续 Ray Query 效果

实施顺序：

1. Contact shadow / sun shadow。
2. RTAO。
3. 单次反射 ray。
4. 混合 RT reflection。
5. 低样本 RTGI 实验。

## 11. 阶段七：完整 Ray Tracing Pipeline

完整 RT Pipeline 仅在 Ray Query 无法满足着色需求时加入。

需要新增：

- RayGen、Miss、ClosestHit、AnyHit、Intersection 和 Callable shader stage。
- RT shader group。
- RT pipeline description。
- shader group handle query。
- Shader Binding Table buffer usage 与 alignment。
- SBT region description。
- `traceRays` 和 `traceRaysIndirect` command。
- recursion depth 与 payload size 限制。

该阶段适用于：

- 复杂多材质反射。
- 多次 bounce 实验。
- 程序化 primitive。
- path tracing debug mode。
