## 1. 升级背景与总体目标

### 1.1 升级动机

Mecraft 红石系统已完成基础信号传播、逻辑门元件、时序元件、机械元件等核心功能，并采纳 Bedrock 的确定性更新队列与 Java 的 10 Hz 红石刻。然而，原版红石在空间利用率上存在两个根本性瓶颈：

| 瓶颈 | 原版表现 | 玩家痛点 |
|------|---------|---------|
| **线缆隔离** | 所有红石粉共享同一信号通道，相邻线缆会互相连接 | 复杂电路必须用方块隔开，空间利用率低，"红石机械体积大" |
| **空间维度单一** | 红石粉只能放在方块顶面（floor），无法利用墙面与天花板 | 电路只能水平铺开，垂直空间浪费 |
| **单方块单线** | 一个方块空间内最多一条红石线 | 线缆密度受限于方块密度，无法在 1 格内走多路线缆 |

### 1.2 三大升级目标

本指导文档针对上述瓶颈提出三项**超越原版**的增强特性：

| 特性 | 核心能力 | 原版/模组对照 |
|------|---------|--------------|
| **A. 多色红石线** | 不同颜色的红石线互相绝缘，只有同色才连接 | 原版无；Project Red 的 insulated wire 类似 |
| **B. 爬墙/天花板红石线** | 红石线可放置在方块侧面（墙面）与底面（天花板），并能跨越棱角连接 | 原版只有顶面 + 向上爬升；无天花板 |
| **C. 红石微方块 + 多部件容器** | 单个方块空间内可容纳多条独立线缆（不同色/不同面），互不干扰 | 原版无；Project Red 的 bundled cable、Immibis 微方块 |

### 1.3 与原版的差异定位

Mecraft 红石系统的设计哲学是"**可预测、高密度、空间友好**"。三大升级正是这一哲学的延伸：

- 多色线缆：用颜色隔离替代空间隔离，提升密度
- 爬墙/天花板：把电路从"二维平面"扩展到"三维空间"
- 微方块多部件：把"一方块一线缆"扩展到"一方块多线缆"

这三者共同将红石机械的体积压缩到原版的 1/3 ~ 1/10，同时保持图灵完备性与确定性。

## 2. 当前红石系统能力与限制分析

### 2.1 已具备的能力（可直接复用）

| 能力 | 实现位置 | 说明 |
|------|---------|------|
| 多色红石通道 | `BlockDef.redstoneWireChannel` / `redstoneWireChannelId` / `redstoneWireTint` | 已落地红色、蓝色两色，同色才连接 |
| `facing` 多面属性 | `PropIndices::FACING_FLOOR/NORTH/SOUTH/EAST/WEST/UP/DOWN` | 属性注册表已支持 7 种朝向 |
| `face_plane_wall` 放置策略 | `Placement.cpp:431` | 藤蔓、glow_lichen 已用于墙面放置 |
| `attached_face` 支撑规则 | `BlockDef.supportRule` | 方块支撑面检查已存在 |
| 方块实体存储 | `BlockEntityInventoryStore` | 按位置存储附加数据（最多 54 槽位），可扩展为通用 BlockEntity |
| 方块实体渲染器 | `BlockEntityRenderer` | 已存在，支持方块实体独立渲染 |
| 异形方块模型 | `mecraft_model_v1` 格式 + `MeshBuilderRegistry` | 自研 JSON 模型，支持 from/to/faces 元素 |
| 确定性更新队列 | `RedstoneUpdateQueue` + `BlockNeighborUpdateQueue` | Bedrock 风格固定顺序 |
| 信号衰减 | `kMaxRedstonePower = 15`，每格 -1 | 线材传导标准模型 |
| 网络同步 | `BlockChangeCallback` | 方块状态变化自动同步，无需额外协议 |
| 存档 | `ChunkSerializer` 序列化完整 `StateID` | 状态变化自动持久化 |

### 2.2 当前的限制（需改造的硬编码点）

#### 限制 1：红石线 `facing` 只有 `floor`

`assets/config/blocks.json:1028`：
```json
"properties": {
    "facing": ["floor"],
    ...
}
```
红石线的 `facing` 属性被限制为只有 `floor` 一个值，无法表达墙面/天花板朝向。

#### 限制 2：渲染器硬编码 floor 检查

`src/renderer/mesh/ChunkMesher.cpp:3619-3622`：
```cpp
const uint16_t facing = BlockStateRegistry::getPropertyIndex(blockId, PropIndices::FACING);
if (facing != PropIndices::FACING_FLOOR) {
    return;  // 当前直接跳过非 floor 红石线的渲染
}
```
`buildRedstoneWire` 只渲染地面红石线，墙面/天花板红石线即使存在也不会被绘制。

#### 限制 3：连接逻辑只处理水平面 + 向上爬升

`src/ecs/systems/world/RedstoneSystem.cpp:543-571` 的 `forEachWireNeighbor`：
```cpp
// 6 cardinal directions (含上下)
for (const glm::ivec3& direction : kDirections) { ... }
// 水平 4 方向的爬升/下降
for (const glm::ivec3& hDir : kHorizontalDirections) {
    if (isSolidBlockState(neighborState)) {
        // 检查上方是否有线（爬升）
    } else {
        // 检查下方是否有线（下降）
    }
}
```
该函数**只考虑水平面的 4 个方向**做爬墙判断，完全没有"墙面红石线在墙平面内的连接"和"天花板红石线的连接"逻辑。

#### 限制 4：放置策略 `face_plane_floor` 限定地面

`blocks.json:1047`：
```json
"placementStrategy": "face_plane_floor"
```
`Placement.cpp:439-445` 的 `strategyFacePlaneFloor` 仅当 `hitNormal.y == 1` 时返回有效状态，即只能在地面放置。

#### 限制 5：连接属性 `north/south/east/west` 语义是"水平方向"

`blocks.json:1030-1033`：
```json
"north": ["none", "side", "up"],
"south": ["none", "side", "up"],
"east":  ["none", "side", "up"],
"west":  ["none", "side", "up"]
```
四个属性的取值 `none/side/up` 是为**地面红石线**设计的：
- `none`：该方向无连接
- `side`：该方向水平连接到同高度线缆
- `up`：该方向向上爬升（连接到高一格的线缆）

这个语义模型无法表达"墙面红石线沿墙面向上/向下/向左/向右连接"。

#### 限制 6：单方块单线缆

当前一个方块位置只能存在一个 `redstone_wire` 方块状态。要在同一位置放第二条线缆，必须替换原方块。这是原版红石的根本限制，也是特性 C 要解决的核心问题。

### 2.3 改造影响面评估

| 改造点 | 影响文件 | 影响范围 |
|--------|---------|---------|
| 红石线 `facing` 扩展 | `blocks.json`、`PropIndices.h`、`BlockStateRegistry` | 数据层，低风险 |
| 渲染器支持多面 | `ChunkMesher.cpp` 的 `buildRedstoneWire` | 渲染层，中风险 |
| 连接逻辑泛化 | `RedstoneSystem.cpp` 的 `forEachWireNeighbor`、`propagateWirePower` | 逻辑层，中高风险 |
| 放置策略 | `Placement.cpp` 新增 `redstone_wire_multi_face` | 交互层，低风险 |
| 微方块多部件 | 新增 `BlockPartContainer` 系统 + `BlockEntity` 扩展 | 架构层，高风险 |

## 3. 设计原则与架构约束

### 3.1 必须遵守的项目原则（来自 AGENTS.md）

- **禁止任何 fallback/兜底代码**：出现 bug 必须修复根因，不允许"降级处理""如果没有就回退"
- **C++17 标准**，多使用现代 C++ 特性
- **代码注释必须用英文**，必须清晰描述函数目的、参数意义、返回值含义、算法思路
- **汇报文档用中文**
- **数据驱动优先**：新增方块/行为通过 JSON 配置，不改 C++ 热路径
- **热路径用缓存 ID**：启动时 `findByName` 查询并缓存，运行时不做哈希查询
- **服务器权威**：方块交互服务端校验并执行，客户端不直接改世界
- **确定性优先**：固定更新顺序，无 QR 链玄学
- **网络同步复用 `BlockChangeCallback`**，存档复用 `ChunkSerializer`

### 3.2 本次升级的特有原则

1. **向后兼容现有红石机器**：现有的地面红石线行为必须完全不变。新增的墙面/天花板红石线是**扩展**，不是替换。
2. **颜色隔离是强约束**：不同颜色的红石线在任何情况下都不连接，包括跨棱角、跨微方块部件。
3. **一方块多线缆不能破坏方块语义**：承载多线缆的"微方块容器"必须仍然是一个方块（有碰撞箱、可破坏、可被活塞推动），线缆是它的"部件"。
4. **可视化优先**：玩家必须能直观看到每条线缆的颜色、走向、信号强度。渲染不能因多线缆而混乱。
5. **性能不退化**：多线缆场景下，BFS 传播、网格生成、网络同步的复杂度应保持线性级，避免指数爆炸。

### 3.3 命名规范（与现有一致）

- 命名空间化 ID：`minecraft:redstone_wire`、`minecraft:redstone_wire_container`
- C++ 类名 PascalCase：`RedstoneWireContainer`、`BlockPartContainer`
- 方法/变量 camelCase：`forEachWireNeighbor`、`wireChannelId`
- JSON 字段 camelCase：`redstoneBehavior`、`redstoneWireChannel`、`redstoneWireTint`
- 红石行为字段值：`"wire"`、`"wire_container"`（新增）
- 朝向值：`floor`、`north`、`south`、`east`、`west`、`up`、`down`（已存在）

## 4. 特性 A：多色红石线（已实现，扩展指南）

### 4.1 当前实现回顾

多色红石线已落地，核心机制如下：

#### 4.1.1 数据驱动字段

`BlockDef`（`src/world/block/Block.h`）已包含：
```cpp
std::string redstoneWireChannel;   // e.g. "minecraft:red", "minecraft:blue"
uint16_t redstoneWireChannelId;    // 加载期解析为整数，热路径比较
uint8_t redstoneWireTint;          // shader 调色板槽位 [0,15]
```

#### 4.1.2 已注册的颜色

| 方块 ID | channel | tint | 掉落物 |
|---------|---------|------|--------|
| `minecraft:redstone_wire` | `minecraft:red` | 0 | `minecraft:redstone` |
| `minecraft:blue_redstone_wire` | `minecraft:blue` | 1 | `minecraft:blue_redstone` |

#### 4.1.3 颜色隔离机制

`RedstoneSystem.cpp:216-222`：
```cpp
bool isMatchingWireState(const StateID stateId, const uint16_t wireChannelId) {
    if (!isWireState(stateId)) {
        return false;
    }
    const BlockID blockId = BlockStateRegistry::getBlockId(stateId);
    return BlockRegistry::getFast(blockId).redstoneWireChannelId == wireChannelId;
}
```
`forEachWireNeighbor` 在遍历邻居时，只对 `isMatchingWireState(neighbor, selfChannelId)` 为真的邻居调用回调。不同颜色的线缆即使相邻也不会连接。

#### 4.1.4 渲染色调

`ChunkMesher.cpp:3661-3663`：
```cpp
renderData.tintKind = BlockTintKinds::REDSTONE;
renderData.tintU = static_cast<uint8_t>(power << 4U);      // 信号强度决定亮度
renderData.tintV = static_cast<uint8_t>(def.redstoneWireTint << 4U);  // 颜色决定色相
```
shader 通过 `tintV` 选择调色板槽位，实现不同颜色的着色。

### 4.2 扩展新颜色的标准流程

新增一种颜色（如绿色 `minecraft:green`）只需**纯数据驱动**，无需改 C++：

1. **在 `blocks.json` 添加方块定义**（复制蓝色线，改 channel/tint/drop/id）：
```json
{
  "id": "minecraft:green_redstone_wire",
  "drop": "minecraft:green_redstone",
  "redstoneBehavior": "wire",
  "redstoneWireChannel": "minecraft:green",
  "redstoneWireTint": 2,
  "isRedstoneConductor": false,
  "properties": { /* 与 redstone_wire 相同 */ },
  "defaultState": { /* 与 redstone_wire 相同 */ },
  "isSolid": false,
  "isTransparent": true,
  "renderLayer": "cutout",
  "allowsFluidCoexistence": true,
  "placementStrategy": "face_plane_floor",
  "supportRule": "attached_face",
  "renderShape": "redstone_wire",
  "textures": { /* 复用 redstone_dust_* 贴图 */ }
}
```

2. **在物品配置中添加对应物品**（`green_redstone` 物品，放置时变成 `green_redstone_wire`）。

3. **在 shader 调色板中添加 tint=2 的颜色映射**（`redstone_tint.glsl` 或材质配置）。

4. **添加测试**（参考 `tests/redstone_multicolor_test.cpp` 若有，或复制蓝色测试改色）。

### 4.3 多色与电源/设备的兼容性

当前设计：**所有颜色的线缆共享同一套电源与设备**。即拉杆、按钮、红石火把等电源会同时驱动所有颜色的相邻线缆。

**原理**：电源方块的 `isRedstonePowerSource = true` 不区分颜色。`forEachWireNeighbor` 在判断"邻居是否为可连接线缆"时检查颜色匹配，但电源是通过**直接传导**（非线材传导）给相邻方块供电的，不走颜色匹配逻辑。

**若需要"颜色专用电源"**（如蓝色拉杆只驱动蓝线）：在 `BlockDef` 新增 `redstoneWireChannel` 字段给电源方块，电源输出时只激活匹配颜色的相邻线缆。这是后续可选增强，当前不实现。

## 5. 特性 B：爬墙/天花板红石线

### 5.1 设计目标

让红石线能够：
1. 放置在方块**侧面**（墙面，4 个水平方向），如同藤蔓贴墙
2. 放置在方块**底面**（天花板），向下悬挂
3. 跨越**棱角**连接：地面线 → 沿墙向上 → 跨过墙顶 → 沿另一面墙向下，形成连续电路
4. 墙面线在墙平面内沿四个方向连接（上/下/左/右）
5. 天花板线在天花板平面内沿四个方向连接

### 5.2 与原版"向上爬升"的区别

原版红石线的 `up` 连接（`north/south/east/west = up`）是指：**线缆在地面，向上爬到高一格的固体方块侧面**。线缆本体仍在地面，只是视觉上沿墙面向上画一段。

Mecraft 的"爬墙红石线"是：**线缆本体贴在墙面，整条线缆在垂直平面内延伸**。这是质的区别，原版没有这个能力。

### 5.3 朝向模型设计

#### 5.3.1 扩展 `facing` 属性取值

红石线的 `facing` 属性从 `["floor"]` 扩展为 6 个值：

| facing 值 | 含义 | 线缆所在平面 | 贴附的方块面 |
|-----------|------|-------------|-------------|
| `floor` | 地面（顶面贴附） | XZ 平面（水平） | 下方方块的顶面 |
| `ceiling` | 天花板（底面贴附） | XZ 平面（水平） | 上方方块的底面 |
| `north` | 北墙（北面贴附） | XY 平面（垂直） | 北侧方块的南面 |
| `south` | 南墙 | XY 平面 | 南侧方块的北面 |
| `east` | 东墙 | YZ 平面 | 东侧方块的西面 |
| `west` | 西墙 | YZ 平面 | 西侧方块的东面 |

`PropIndices::FACING_FLOOR/NORTH/SOUTH/EAST/WEST/UP/DOWN` 中，`UP`/`DOWN` 可分别对应 `ceiling`/`floor` 的别名，或新增 `FACING_CEILING`。**推荐复用 `FACING_DOWN` 表示 ceiling（线缆向下挂，贴附上方方块）**，`FACING_FLOOR` 保持表示地面，避免新增常量。但为语义清晰，**建议新增 `FACING_CEILING`** 并在 `PropIndices.h` 注册。

#### 5.3.2 连接属性泛化

当前 `north/south/east/west` 四个属性是**世界坐标方向**，取值 `none/side/up`。这个模型对墙面/天花板红石线不适用。

**方案：保留世界坐标方向，但泛化取值语义**。

将 `north/south/east/west` 的取值从 `none/side/up` 扩展为 `none/side/up/down`：
- `none`：该世界方向无连接
- `side`：该世界方向水平/同面连接（适用于 floor/ceiling/wall）
- `up`：该世界方向向上连接（爬升或墙面纵向）
- `down`：该世界方向向下连接（下降或墙面纵向，新增）

但这样对墙面线缆仍不够表达。墙面线缆在墙平面内的"左右"方向需要映射到世界方向。

**更清晰的方案：引入"局部连接坐标"**。新增属性 `conn_a`/`conn_b`/`conn_c`/`conn_d` 表示线缆在**自身平面内的四个方向**，取值 `none/side/corner`：
- `conn_a`：平面内"第一轴正方向"
- `conn_b`：平面内"第一轴负方向"
- `conn_c`：平面内"第二轴正方向"
- `conn_d`：平面内"第二轴负方向"

每个 `facing` 值定义自己的局部坐标系：

| facing | 第一轴 | 第二轴 | 平面法线 |
|--------|--------|--------|---------|
| `floor` | +X (east) | +Z (south) | +Y (up) |
| `ceiling` | +X (east) | +Z (south) | -Y (down) |
| `north` | +X (east) | +Y (up) | +Z (south, 指向墙外) |
| `south` | +X (east) | +Y (up) | -Z (north, 指向墙外) |
| `east` | +Z (south) | +Y (up) | -X (west, 指向墙外) |
| `west` | +Z (south) | +Y (up) | +X (east, 指向墙外) |

**决策：采用方案二（局部连接坐标）**，理由：
- 语义清晰，墙面/天花板/地面统一处理
- 渲染器只需根据 `facing` 旋转局部连接到世界坐标
- 连接逻辑可泛化为"在自身平面内找 4 个邻居"

**但为了向后兼容现有地面红石线**，保留 `north/south/east/west` 属性用于 `facing=floor`，新增 `conn_a/b/c/d` 用于 `facing != floor`。渲染器和逻辑层根据 `facing` 选择读取哪组属性。

> ⚠️ **折中决策**：为避免属性爆炸，**统一使用 `north/south/east/west` 四个属性，但根据 `facing` 重新解释其世界方向语义**。例如 `facing=north`（北墙）时，`north` 属性表示"沿墙面向上"，`south` 表示"沿墙面向下"，`east`/`west` 表示"沿墙面向东/西"。这样无需新增属性，只需在连接逻辑和渲染器中根据 `facing` 做坐标变换。**本方案采纳此折中**，详见第 8 章数据结构。

### 5.4 跨棱角连接

爬墙红石线的核心价值在于**跨越棱角**。例如：

```
     红石线（贴北墙，facing=north）
        ↑
        │
  ──────●────── 地面红石线（facing=floor）
  （地面）│
        │
     （北墙）
```

地面线在 `(x, y, z)`，facing=floor；墙面线在 `(x, y+1, z)`，facing=north（贴在 `(x, y+1, z-1)` 方块的南面）。两者在 `(x, y, z)` 与 `(x, y+1, z)` 之间形成"地面→墙面"的棱角连接。

**棱角连接规则**（确定性，参考藤蔓但扩展为双向）：
1. 两条红石线**同色**
2. 两条线缆的 `facing` 对应的**贴附方块**相邻（共享一个棱）
3. 两条线缆在棱角处都"伸向"对方

具体地，定义 `faceNormal(facing)` 为线缆贴附方块的面的外法线（指向线缆所在空间）：

| facing | faceNormal（指向线缆空间） |
|--------|--------------------------|
| floor | (0, 1, 0) |
| ceiling | (0, -1, 0) |
| north | (0, 0, 1) |
| south | (0, 0, -1) |
| east | (-1, 0, 0) |
| west | (1, 0, 0) |

两条线缆 A（在 `posA`，facing=`fA`）和 B（在 `posB`，facing=`fB`）能棱角连接的条件：
- `posB - posA` 是 `fA` 的 faceNormal 或 `fB` 的 faceNormal 的反向（即两者共享一个棱）
- 且该棱处的两个方块面都允许线缆通过（非固体阻挡）

### 5.5 放置规则

#### 5.5.1 新增放置策略 `redstone_wire_face`

### 5.6 连接逻辑改造

#### 5.6.1 `forEachWireNeighbor` 泛化

当前 `forEachWireNeighbor`（`RedstoneSystem.cpp:543`）只处理水平面 + 向上爬升。需重构为**基于 `facing` 的局部坐标系邻居查找**：

```cpp
// Pseudo-code for generalized wire neighbor iteration
template <typename Fn>
void forEachWireNeighbor(const World& world, const glm::ivec3& pos, Fn&& fn) {
    const StateID selfState = world.getBlockState(pos.x, pos.y, pos.z);
    if (!isWireState(selfState)) return;
    const uint16_t selfChannel = redstoneWireChannelIdForState(selfState);
    const uint16_t selfFacing = getRequiredProperty(selfState, PropIndices::FACING, "facing");

    // 1. Same-plane neighbors (4 directions within the wire's own plane)
    for (const auto& [localDir, worldDir] : planeDirectionsFor(selfFacing)) {
        const glm::ivec3 neighbor = pos + worldDir;
        const StateID nState = world.getBlockState(neighbor.x, neighbor.y, neighbor.z);
        if (isMatchingWireState(nState, selfChannel)) {
            const uint16_t nFacing = getFacing(nState);
            // Only connect if neighbor is on the same plane (same facing)
            // OR on an adjacent plane via corner (handled in step 2)
            if (nFacing == selfFacing) {
                fn(neighbor);
            }
        }
    }

    // 2. Corner connections (cross-edge to adjacent planes)
    // The wire's faceNormal points into open space. Adjacent positions along
    // the face's edges may host wires on perpendicular faces.
    const glm::ivec3 faceNormal = faceNormalFor(selfFacing);
    // Check the 4 edge-adjacent positions (faceNormal + each of 2 plane axes ±)
    // ... see algorithm in section 9
}
```

#### 5.6.2 爬墙/天花板内的"爬升/下降"

墙面红石线（`facing=north`）在墙平面内可以"向上"（+Y）和"向下"（-Y）连接，这是平面内连接，不需要特殊爬升逻辑。但墙面线遇到**墙顶**时，可以跨越到地面线（facing=floor），这是棱角连接（见 5.4）。

天花板红石线（`facing=ceiling`）在天花板平面内水平连接，遇到墙顶时跨越到墙面线。

### 5.7 渲染改造

#### 5.7.1 `buildRedstoneWire` 多面支持

当前 `ChunkMesher.cpp:3619-3622` 硬编码 `if (facing != FACING_FLOOR) return;`。需移除该检查，并根据 `facing` 旋转线缆网格：

```cpp
// Pseudo-code
void buildRedstoneWire(ChunkMeshData& meshData, const Snapshot& snapshot,
                       BlockID blockId, const BlockDef& def, int x, int y, int z) {
    const uint16_t facing = getPropertyIndex(blockId, FACING);
    // Compute the 4 connection levels in the wire's local plane
    auto [connA, connB, connC, connD] = readConnections(blockId, facing);
    // Build the wire geometry in local space (XZ plane, like floor)
    // Then rotate by the facing->world transform
    const glm::mat3 rot = wireFaceRotation(facing);
    emitWireGeometry(meshData, connA, connB, connC, connD, rot, def.redstoneWireTint, power);
}
```

#### 5.7.2 贴图复用

红石线的 dot/line0/line1/overlay 贴图在局部坐标系内复用，通过旋转矩阵变换到世界坐标。无需为每个 `facing` 单独制作贴图。

### 5.8 与多色的兼容

爬墙/天花板红石线**完全兼容多色**。颜色隔离通过 `redstoneWireChannelId` 实现，与 `facing` 正交。即：红色墙面线只连接红色墙面线（或红色地面线经棱角），不连接蓝色墙面线。

## 6. 特性 C：红石微方块 + 多部件容器（单方块多线缆）

### 6.1 问题陈述

特性 A（多色）解决了"不同色线缆互相干扰"，但**同色的两条线缆**仍不能在同一方块空间共存。例如，红石机械中常见的"两条平行的红线"必须间隔 1 格方块。

特性 C 的目标：**让一个方块空间内能容纳多条独立线缆**，每条线缆有自己的颜色、朝向、信号强度，互不影响。

这是爬墙红石线（特性 B）的**必要前提**：红石线爬墙后，在墙壁内角处，需要两条不同朝向的线缆在同一方块空间交汇（一条贴 A 墙，一条贴 B 墙），否则无法形成连续电路。

### 6.2 模组参考分析

| 模组 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **Project Red - Transmission** | Bundled Cable：单方块内 16 色线缆束，用染色绝缘线连接 | 密度极高，1 格 16 线 | 只支持地面，颜色固定 16 种 |
| **Immibis's Microblocks** | 将方块空间分为若干 slot（6 面薄片 + 中心），每个 slot 放一个微方块 | 通用微方块系统，支持任意薄方块 | 槽位有限，红石逻辑需额外处理 |
| **RedLogic** | 类似 Immibis，微方块 + 多色线 | 灵活 | 复杂度高 |
| **Create - Gantry** | 链条/管道，不同维度 | 视觉清晰 | 不是传统红石语义 |

### 6.3 Mecraft 方案：`wire_container` 方块 + `BlockPartContainer` 部件系统

**核心思路**：引入一种新方块 `minecraft:wire_container`（线缆容器），它本身是一个完整方块（有碰撞箱、可破坏、可被活塞推动），但其内部维护一个**部件列表**，每个部件是一条独立的红石线缆（有 color、facing、power、connections）。

#### 6.3.1 为什么不用微方块 slot 系统？

Immibis 风格的微方块 slot 系统虽然通用，但：
1. 需要重构整个方块的存储模型（当前一个位置 = 一个 StateID）
2. 与现有贪心网格、光照、碰撞系统冲突
3. 红石线缆只需要"在方块内存储多条独立线缆"，不需要完整的微方块通用性

因此 Mecraft 采用**专用线缆容器**而非通用微方块系统，保持架构简单。

#### 6.3.2 部件数据模型

每个 `wire_container` 方块关联一个 `WireContainerParts` 数据结构（存储在 BlockEntity 中）：

```cpp
/// A single wire part inside a wire_container block.
/// Each part is an independent redstone wire with its own color, facing, and power.
struct WirePart {
    uint16_t channelId;     // redstoneWireChannelId (color identity)
    uint16_t facing;        // PropIndices::FACING_* (which face of the container)
    uint8_t  power;         // 0-15 signal strength
    uint8_t  connections;   // bitmask: 4 bits for 4 local directions (a/b/c/d)
};

/// All wire parts hosted by a single wire_container block.
/// Stored as a BlockEntity attached to the block position.
class WireContainerParts {
public:
    /// Add a wire part. Returns false if a part with the same (channelId, facing) exists.
    bool addPart(const WirePart& part);
    /// Remove the part with the given (channelId, facing). Returns true if removed.
    bool removePart(uint16_t channelId, uint16_t facing);
    /// Find a part by (channelId, facing). Returns nullptr if not found.
    const WirePart* find(uint16_t channelId, uint16_t facing) const;
    /// Iterate all parts.
    template <typename Fn> void forEach(Fn&& fn) const;
    /// Maximum parts per container (e.g., 24 = 6 faces × 4 colors).
    static constexpr size_t MAX_PARTS = 24;

private:
    std::array<WirePart, MAX_PARTS> m_parts;
    uint8_t m_count = 0;
};
```

#### 6.3.3 容量限制

每个 `wire_container` 最多容纳的线缆部件数：
- **按"每面每色一条"**：6 面 × N 色 = 6N。当前 2 色 → 12 部件；扩展到 4 色 → 24 部件。
- `MAX_PARTS = 24` 足够，且内存占用固定（24 × 6 字节 = 144 字节/方块）。

**约束**：同一 `(channelId, facing)` 组合只能有一条线缆（不允许同面同色两条）。这保证部件可由 `(channelId, facing)` 唯一索引。

### 6.4 与特性 B 的关系

特性 C 的 `WirePart.facing` 复用特性 B 的 facing 语义（floor/ceiling/north/south/east/west）。即：容器内的每条线缆都"贴"在容器的某个面上，有自己的朝向和连接。

**墙壁内角示例**：
```
       墙A（北墙）
        │
   ┌────●────┐  ← wire_container at (x, y, z)
   │ part1:  │     part1: channelId=red, facing=north (贴墙A)
   │ facing= │     part2: channelId=red, facing=east  (贴墙B)
   │ north   │     两条红线在容器内共存，但各自沿不同墙延伸
   │ part2:  │
   │ facing= │
   │ east    │
   └─────────┘
        │
       墙B（东墙）
```
没有特性 C，墙角处只能放一条线缆，电路无法拐弯。

### 6.5 信号传播：容器内 vs 容器间

#### 6.5.1 容器内：部件之间不直接传导

容器内的多条线缆**互相绝缘**，即使颜色相同也不在容器内连接。理由：
- 部件已由 `(channelId, facing)` 唯一标识，若同色同面会有歧义
- 玩家放置线缆时，意图是让线缆沿特定方向延伸，而非在容器内"短路"

**例外**：若未来需要"容器内转接"（如红线从 floor 面转到 north 面），可通过专门的"转接部件"实现，但不在本期范围。

#### 6.5.2 容器间：按 (channelId, facing) 匹配连接

容器 A 的部件 `(ch, fA)` 与相邻容器 B 的部件 `(ch, fB)` 连接的条件：
1. `ch` 相同（同色）
2. `fA` 与 `fB` 满足"同面连接"或"棱角连接"规则（与特性 B 的普通红石线一致）

即：把每个 `WirePart` 视为一条贴在容器某面的普通红石线，连接规则完全复用特性 B 的逻辑。

#### 6.5.3 容器与普通红石线的互操作

`wire_container` 旁边的普通红石线（`redstone_wire`）应能与容器内匹配颜色和朝向的部件连接。这要求 `forEachWireNeighbor` 同时识别普通线缆和容器部件。

### 6.6 放置与交互

#### 6.6.1 放置流程

玩家手持红石粉右键点击：
1. 若点击位置是空气，且贴附方块有效 → 放置普通 `redstone_wire`（特性 B 行为）
2. 若点击位置已有 `wire_container` → 向容器添加新部件（颜色由红石粉物品决定，朝向由点击面决定）
3. 若点击位置已有普通 `redstone_wire` → **替换为 `wire_container`**，将原线缆作为第一个部件，再添加新部件

这需要 `PlacementStrategyRegistry` 的 `tryMergePlacementStates` 机制（`Placement.cpp:449`）支持"普通线缆 → 容器"的升级合并。

#### 6.6.2 破坏与拾取

破坏 `wire_container` 时：
- 若容器内只有 1 个部件 → 退化为普通 `redstone_wire`，掉落对应红石粉
- 若容器内有多个部件 → 掉落所有部件对应的红石粉，方块变为空气

破坏交互（左键）应区分"破坏整个容器"还是"移除单个部件"。**建议**：左键破坏整个容器；新增"扳手/钳子"工具的右键交互用于移除单个部件（按点击面 + 颜色）。本期可先实现整体破坏，部件级操作作为后续增强。

### 6.7 渲染

#### 6.7.1 渲染策略

`wire_container` 的渲染**不走标准贪心网格**，而是走 `BlockEntityRenderer` 或专用的 `renderShape: "wire_container"`。理由：
- 容器内有多条线缆，每条有自己的连接状态，无法用单一 StateID 表达
- 线缆几何需根据 `WireContainerParts` 动态生成

在 `MeshBuilderRegistry` 注册 `"wire_container"` builder，遍历 `WireContainerParts`，为每个部件调用特性 B 的线缆几何生成函数（带 facing 旋转 + tint）。

#### 6.7.2 容器本体视觉

容器方块本身可以：
- **不可见**（纯逻辑容器，只渲染内部线缆）—— 视觉上等同于多条线缆堆叠
- **半透明框架**（细线框表示容器边界）—— 帮助玩家理解"这里是容器"

**推荐**：默认不可见，仅渲染内部线缆。若玩家手持"扳手"或开启调试视图，显示半透明框架。

#### 6.8.1 复用 `BlockEntityInventoryStore` 模式

`BlockEntityInventoryStore`（`src/game/inventory/BlockEntityInventoryStore.h`）已实现"按位置存储附加数据"的模式。`WireContainerParts` 采用相同模式：

## 9. 算法设计：多面线缆连接与信号传播

### 9.1 邻居查找算法（泛化版）

/// Enumerate all wire positions connected to the wire at pos.
/// Handles same-plane connections, corner (edge) connections, and
/// wire_container parts. Each connected wire is passed to fn.

### 9.2 棱角连接判定

```cpp
/// Determine if wire A at posA (facing fA) and wire B at posB (facing fB)
/// form a valid corner connection.
///
/// A corner connection exists when:
/// - posA and posB are adjacent (differ by exactly 1 in one axis).
/// - The shared edge belongs to both wires' planes.
/// - Both wires' faceNormals are perpendicular (not parallel, not opposite).
///
/// @return True if the two wires connect across the corner.
bool isCornerConnection(const glm::ivec3& posA, uint16_t fA,
                        const glm::ivec3& posB, uint16_t fB) {
    const glm::ivec3 delta = posB - posA;
    const int manhattan = std::abs(delta.x) + std::abs(delta.y) + std::abs(delta.z);
    if (manhattan != 1) return false;  // Must be adjacent

    const glm::ivec3 nA = WireFaceGeometry::faceNormal(fA);
    const glm::ivec3 nB = WireFaceGeometry::faceNormal(fB);

    // The delta must align with one of the face normals (the edge direction)
    const bool deltaIsA = (delta == nA || delta == -nA);
    const bool deltaIsB = (delta == nB || delta == -nB);
    if (!deltaIsA && !deltaIsB) return false;

    // Face normals must be perpendicular (dot product zero)
    return glm::dot(nA, nB) == 0;
}
```

### 9.3 信号传播 BFS（多面版）

复用现有 `propagateWirePower` 的 BFS 框架，仅将邻居查找替换为泛化版 `forEachWireNeighbor`：

```cpp
/// BFS power propagation generalized for multi-face and multi-part wires.
/// Same algorithm as existing propagateWirePower, but uses the generalized
/// forEachWireNeighbor that handles floor/ceiling/wall/corner/container.
///
/// @param world    Read-only world.
/// @param sources  Initial (position, power) pairs from power sources.
/// @return Map of wire positions to their new power levels.
std::unordered_map<glm::ivec3, uint8_t>
propagateWirePowerMultiFace(const World& world,
                            const std::vector<RedstoneSource>& sources) {
    // Priority queue (max-heap by power)
    std::priority_queue<PowerNode> frontier;
    WirePowerMap bestPower;

    // Seed with sources
    for (const auto& src : sources) {
        if (src.power == 0) continue;
        frontier.push({src.position, src.power});
        bestPower.set(src.position, src.power);
    }

    while (!frontier.empty()) {
        const PowerNode node = frontier.top();
        frontier.pop();
        if (!bestPower.isCurrent(node.position, node.power)) continue;

        const uint8_t nextPower = (node.power > 0) ? static_cast<uint8_t>(node.power - 1) : 0;
        if (nextPower == 0) continue;

        forEachWireNeighbor(world, node.position, [&](const glm::ivec3& neighbor) {
            if (bestPower.wasEvaluated(neighbor)) return;
            uint8_t& existing = bestPower.emplace(neighbor);
            if (existing < nextPower) {
                existing = nextPower;
                frontier.push({neighbor, nextPower});
            }
        });
    }

    return bestPower.powers;
}
```

### 9.4 容器部件的邻居查找

当 `forEachWireNeighbor` 遇到 `wire_container` 方块时，需查询其 `WireContainerParts`，对每个匹配 `(channelId, facing)` 的部件分别判断连接：

```cpp
// Inside forEachWireNeighbor, when checking a neighbor position:
const StateID nState = world.getBlockState(neighbor.x, neighbor.y, neighbor.z);
const BlockDef& nDef = BlockRegistry::getFast(BlockStateRegistry::getBlockId(nState));

if (nDef.isWireContainer) {
    // Query the container's parts
    const WireContainerParts* parts = world.wireContainerParts().find(neighbor);
    if (parts == nullptr) return;  // No parts (should not happen for valid container)
    parts->forEach([&](const WirePart& part) {
        if (part.channelId != selfChannel) return;
        // Check if this part connects to self via same-plane or corner rules
        if (canConnect(selfFacing, selfPos, part.facing, neighbor)) {
            fn(neighbor);  // The container position is a connected wire
        }
    });
} else if (isMatchingWireState(nState, selfChannel)) {
    // Ordinary wire neighbor
    const uint16_t nFacing = getFacing(nState);
    if (canConnect(selfFacing, selfPos, nFacing, neighbor)) {
        fn(neighbor);
    }
}
```

### 9.5 确定性保证

所有邻居遍历顺序必须固定：
- `planeNeighborOffsets` 返回的 4 个方向按固定顺序（+axis1, -axis1, +axis2, -axis2）
- 容器部件遍历按 `(channelId, facing)` 升序
- BFS 优先队列的 tiebreaker 用位置坐标字典序

这保证相同输入产生相同输出，无 QR 链。

    EXPECT_EQ(WireFaceGeometry::faceNormal(PropIndices::FACING_EAST),     glm::ivec3(-1, 0, 0));
    EXPECT_EQ(WireFaceGeometry::faceNormal(PropIndices::FACING_WEST),     glm::ivec3(1, 0, 0));
}

TEST(WireFaceGeometry, PlaneAxesArePerpendicularToNormal) {
    for (uint16_t f : {FACING_FLOOR, FACING_CEILING, FACING_NORTH, FACING_SOUTH, FACING_EAST, FACING_WEST}) {
        const auto [a1, a2] = WireFaceGeometry::planeAxes(f);
        const glm::ivec3 n = WireFaceGeometry::faceNormal(f);
        EXPECT_EQ(glm::dot(a1, n), 0);
        EXPECT_EQ(glm::dot(a2, n), 0);
        EXPECT_EQ(glm::dot(a1, a2), 0);  // The two plane axes are perpendicular
    }
}

## 15. 风险与权衡

### 15.1 性能风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| `wire_container` 部件查询开销 | BFS 每次邻居查找需查 `WireContainerPartStore`（哈希表） | 容器方块数量少；可缓存热点容器的部件指针 |
| 渲染开销 | 单容器最多 24 部件几何 | 容器稀疏；网格缓存 |
| 网络带宽 | 部件变化同步 | 每消息 ≤144 字节，仅在变化时发送 |

### 15.2 复杂度风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 连接逻辑泛化引入 bug | 信号传播错误 | 充分单元测试 + 集成测试电路 |
| 棱角连接判定边界情况 | 死循环或漏连 | 严格数学定义 + 测试覆盖所有 facing 组合 |
| 容器与活塞交互 | 活塞推动容器时部件如何处理 | 容器整体移动，部件随之移动（BlockEntity 跟随） |

### 15.3 设计权衡

| 决策 | 选择 | 理由 |
|------|------|------|
| 连接属性 | 复用 `north/south/east/west` 按 facing 重解释 | 避免属性爆炸；向后兼容地面线 |
| 容器部件索引 | `(channelId, facing)` 唯一 | 简单；保证同面同色唯一 |
| 容器内部件是否互连 | 不互连 | 避免歧义；保持"每条线缆独立"语义 |
| 容器本体可见性 | 默认不可见，仅渲染部件 | 视觉等同于多线缆堆叠 |
| 部件级操作 | 本期不实现 | 降低复杂度；后续用扳手工具扩展 |
| 天花板 facing 常量 | 新增 `FACING_CEILING` | 与 `FACING_DOWN` 语义区分清晰 |

### 15.4 与原版红石机器的兼容

- 现有地面红石线行为**完全不变**（facing=floor 走原逻辑路径）
- 现有多色红石线行为**完全不变**
- 新增的墙面/天花板/容器是**增量能力**，不破坏现有电路
