## 1. 性能纪律：先测量，后优化

- **禁止凭感觉优化**：所有改动必须能解释"测得差在哪"，改完必须复测（同机同配置）。
- **禁止为性能牺牲正确性**：优化后 checksum/基准数据变化必须合理解释（例如跨线程合并顺序变化导致 checksum 变更是可接受的，但要有记录）。
- 性能基线 = 仓库内可复现的数据（`tests/perf_baselines/*.json`），不是口头"感觉快了"。

## 2. 测量工具总览

| 工具 | 覆盖 | 位置 |
| --- | --- | --- |
| `DebugFrameProfiler` | CPU：fixedUpdate 各子阶段（输入/状态/粒子/掉落/世界更新）、渲染各子阶段、事件轮询 | `src/game/debug/`，仅 `MECRAFT_DEBUG` 编译 |
| `RenderDebugService` | GPU：22 个 pass 的 GPU 时间戳、剔除统计、加速结构构建时长 | `src/renderer/debug/` |
| `Dashboard` | 运行时 FPS / 帧时间历史（120 采样窗口）、呈现帧率 | `src/ui/Dashboard.cpp`，游戏内叠加层 |
| perf 基准测试 | 离线、可复现的 CPU 吞吐/时延统计 | `tests/*_perf_test.cpp` |

## 3. CPU 帧剖析：DebugFrameProfiler

`DebugFrameProfiler.h`：

- 仅 `#ifdef MECRAFT_DEBUG` 编译，Release 零开销。
- 固定 120 采样历史（`kHistorySamples`），保存每阶段平均与当前帧耗时。
- 覆盖的 CPU 阶段：`fixedUpdateMs / fixedInputMs / fixedStateUpdateMs / fixedParticleUpdateMs / fixedDropUpdateMs / fixedWorldUpdateMs / audioMs / renderMs`，以及更细的渲染分发阶段（`pollEvents / appUpdateDispatch / appRenderDispatch / presentationAcquire / renderSnapshot / renderScene / renderUi / renderDashboard / swapBuffers`）与输入回调（`pollInputCallback / pollCursorPosCallback / pollImgui*`）。

用法：怀疑 CPU 瓶颈 → Debug 构建下跑场景，对比各阶段 ms 占比。占比最大者优先，除非它与预期帧预算无关。

## 4. GPU 计时：RenderDebugService 与 GpuTimerPass

`RenderDebugService.h` 的 `GpuTimerPass` 枚举 22 个计时点：

- 几何：`GBuffer / Shadow / Transparent / Volumetric / Water / Cloud / Reflection / Ssao / Ssgi`
- 光追：`Rtgi / RtgiTrace / RtgiSignalPack`，NRD：`Nrd / NrdGuidePrep / NrdDispatch`
- 加速结构：`SceneTlas / TerrainBlasBuild / TerrainBlasCompaction / AccelerationStructureDynamicPrepare / RtgiSceneTlasBootstrap`
- 后期：`Lighting / Post`

配套机制：

- `GpuFrameStats`：每帧发布的 GPU 时间统计（带单调 `sequence`，避免读到半成品帧）。
- `GpuTimerSegmentToken` / `GpuTimerCheckpoint`：记录一段未提交命令批内的时间戳分配状态，保证**不跨命令批误配计时器**。
- 剔除统计：`FrustumPlane` 六个面相关的裁剪计数。

用法：GPU 瓶颈 → 看 `GpuFrameStats` 各 pass 占比；RTGI/NRD 相关改动必须盯 `rtgiTraceMs / nrdDispatchMs / sceneTlasMs`。

## 5. Dashboard：运行时 FPS 与历史曲线

`src/ui/Dashboard.cpp`：

- 呈现帧率 `presentedFps`、帧时间 `renderMs`、`fpsHistory`（120 采样环形缓冲，画历史曲线）。
- 实时性检查手段：跑固定场景，观察 FPS 与曲线抖动；卡顿抖动 > 波动 → 查 `DebugFrameProfiler` 定位到具体阶段。

## 6. 线程池与并行

`src/thread/ThreadPool.h`：

- `ThreadPool(numThreads)` + `SpinLock`（自旋 + pause/yield 退避），针对**低竞争**任务队列热路径（区块生成/网格化的 push/pop）。
- 使用时注意：
  - 提交的任务必须无共享可变状态或显式同步；
  - 跨线程共享数据（如 `Packet.inProcessPayload` 的 `shared_ptr`）用引用计数传递，**不裸指针跨线程**；
  - 不要提交细到比同步开销还小的任务（粒度参考 `ChunkMeshingService` 按子区块分片）。

## 7. 性能基准测试

机制详见 `07-测试编写规范.md` 第 7 节。要点回顾：

- `tests/*_perf_test.cpp`：warmup + measure，输出 median/avg/p95/min/max + `checksum`。
- 结果写 `tests/perf_baselines/<name>_baseline_<时间戳>.json`，含 `build.config`（固定 Release）。
- **回归对比**：改动后重跑，与最近基线比 median；有回归必须有解释（不得静默）。

## 9. 调优工作流

```
1. 复现：固定场景（地形种子、视距、渲染后端）跑 perf test / 帧剖析
2. 定位：DebugFrameProfiler 分 CPU 阶段；GpuFrameStats 分 GPU pass；取占比最大项
3. 假设：给出"为什么慢"的机制解释（不是"大概慢"）
4. 改动：小步改一处，避免多因素耦合
5. 复测：同配置重跑，对比 baseline JSON
6. 记录：合理则提交（perf(type): ...），不合理则回退，禁止用兜底绕过
7. 回归把关：更新/确认 perf_baselines 与 checksum 可解释
```

## 10. 常见优化模式与禁忌

**推荐模式**：

- 批次化/合并：跨 chunk 合并光照更新（`World::flushInteractiveLighting` 思路）；网格化按子区块分片并行。
- 剔除：视锥剔除统计（`FrustumPlane`）、加速结构动态策略（`DynamicBlasPolicyContract`）。
- 零拷贝：InProcess 传输用 `shared_ptr<Chunk>` 直传，避免序列化（见 06 篇）。
- 避免重复构造：`BlockStateId` 等小值类型按值传递；热路径避免隐式临时字符串。

**禁忌**（违反即违反第 08 篇兜底规则）：

- 用"减少功能"换取帧率（关特性、降采样）而不修复根因；
- 用 `#pragma`/编译器开关压制现象；
- 优化同时悄悄放宽正确性断言（checksum 能帮你抓这个）；
- 提前优化：没有基准支撑的"顺手优化"不提交。
