## 1. 总览：三条更新流水线

一帧（一次主循环迭代）内实际存在**三条节奏不同的流水线**，理解它们的驱动关系是读懂本项目的钥匙：

```
GameManager::run()（每帧一次）
 └─ AppStateMachine.update(frameTime, accumulator)
     └─ GameplayAppState::update
         ├─ [A] while (accumulator >= 1/60) Game::fixedUpdate()   ← 固定步长 60Hz
         │       └─ GameFrameOrchestrator::runFixedUpdate
         │           ├─ 输入采样 → 状态机更新
         │           ├─ 服务器 tick（20Hz 累积，最多 4 tick/步）
         │           ├─ ECS fixedUpdate 系统链
         │           └─ tickClock 驱动 ECS tick 系统（20Hz 节拍器）
         ├─ [B] Game::updateFrame()（每渲染帧一次）
         │       └─ 音频同步、validation 专用逻辑
         └─ [C] Game::renderFrame()（每渲染帧一次）
                 └─ GameFrameOrchestrator::renderFrame
                     ├─ PresentationController.beginFrame（swapchain 获取）
                     ├─ PresentationBuilder.build（ECS → 渲染快照）
                     └─ RenderScene.renderGameplayFrame → RenderGraph 执行
```

| 流水线 | 频率 | 语义 |
| --- | --- | --- |
| [A] fixedUpdate | 固定 60Hz（`kFixedStep = 1/60`） | 模拟稳定：物理、方块交互、战斗、物品、粒子。与渲染帧率解耦 |
| [B] updateFrame | 每渲染帧一次 | 渲染帧率无关逻辑：音频监听同步 |
| [C] renderFrame | 每渲染帧一次 | 全部渲染提交 |
| 服务器 tick | 20Hz（`kServerStep = 1/20`） | 权威模拟：世界方块变化、实体移动、红石、流体 |

固定步长与渲染帧率解耦的经典 accumulator 模式：`updateFrame` 总是以 `accumulator % kFixedStep` 的 alpha 进行插值，渲染时用 `interpolationAlpha` 平滑实体/相机。

## 2. 主循环 GameManager::run

入口：`src/app/GameManager.cpp:563`。每帧：

1. `Time::beginFrame()` — 帧索引 +1。
2. `m_window.pollEvents()` — GLFW 事件轮询，更新 `InputManager` 内部快照。
3. `Time::update()` — 计算 `rawDeltaTime`。
4. 累积 `accumulator += frameTime`（`clampFrameTime` 防止卡顿后大步长）。
5. `m_appStateMachine.update(frameTime, accumulator)` — **游戏逻辑在此**。
6. `m_appStateMachine.render(frameTime)` — **渲染在此**。
7. Benchmark / validation 帧统计；`closeWindowIfBenchmarkComplete`。

要点：

- 主循环**每帧先 update 再 render**，`GameplayAppState` 是当前活跃应用状态（主菜单阶段则是 `MainMenuAppState`，只跑 UI）。
- Streamline（DLSS 3 Frame Gen）在 `MECRAFT_ENABLE_STREAMLINE` 下给帧打 PCL 标记（SimulationStart/End、RenderSubmitStart/End），无 Streamline 时这些代码块为空。

## 3. 游戏内一帧：GameplayAppState

入口：`src/app/states/GameplayAppState.cpp:104`（update）与 `:168`（render）。

`update` 流程：

```
① validation 模式？→ 只跑 updateFrame(0)（渲染由 render 里的 validation 路径驱动），跳过 fixed
② m_game->publishDebugStats()（MECRAFT_DEBUG）
③ while (accumulator >= 1/60)：m_game->fixedUpdate(kFixedStep, accumulator)
   —— 每步之间检查 quit-to-menu 请求
④ m_game->setFixedInterpolationAlpha(accumulator / kFixedStep)
⑤ m_game->updateFrame(frameTime)
```

`render` 流程：

```
① validation 模式？→ 用 ValidationRunController 提供的相机姿态/帧时钟渲染 + 捕获（08 篇详述）
② 正常模式 → m_game->renderFrame(frameTime)
```

> 注意：`Game::fixedUpdate`/`updateFrame`/`renderFrame` 是三个独立入口，内部委托给 `GameFrameOrchestrator`（`src/game/orchestrator/GameFrameOrchestrator.cpp`）。

## 4. fixedUpdate 流水线（60Hz 模拟）

入口：`GameFrameOrchestrator::runFixedUpdate`（`src/game/orchestrator/GameFrameOrchestrator.cpp:89`）。

### 4.1 步骤分解

```
① input.update()：InputManager 刷新 InputSnapshot（当前/前一帧按键状态）
② accumulator -= fixedStep
③ session.receiveWorldMessages()：客户端收取服务器消息（方块变化、实体、掉落物…）
④ 死亡检测：玩家死了按 R → 发送重生请求
⑤ session.stateMachine().update(fixedStep, snapshot)：
     游戏内状态机（GameplayState / UIState / CommandState / SleepingState）
     —— 这里处理交互意图：方块交互、开背包、开命令、打开暂停菜单
⑥ 模拟暂停检查：stateMachine().pausesSimulation() → timeSpeed = 0，跳过后续
⑦ Time::advanceGameTime(scaledFixedStep) —— 推进游戏世界时钟
⑧ 服务器 tick 循环（见第 5 节）
⑨ ECS fixedUpdate 系统链：
     session.gameplayScene().runFixedUpdate(scaledFixedStep)
     —— GameplayPipeline 按注册顺序执行所有 fixed 系统（约 40 个，Client profile）
⑩ session.world().flushInteractiveLighting()：合并玩家位置附近的光照增量
⑪ sendClientInput()：把玩家输入意图打包发给服务器
⑫ ECS tick 循环（见第 5 节）：tickClock.advance → runOneTick()
⑬ 返回 isQuitToMenuRequested()
```

### 4.2 GameplayPipeline 的 fixed 系统顺序（Client profile）

定义在 `GameplayPipeline::buildClientFixedUpdateSystems`（`src/ecs/GameplayPipeline.cpp:72`），顺序即执行顺序，**顺序本身就是数据流**：

| 阶段 | 系统（按注册序） |
| --- | --- |
| 输入与玩家 | `InputSamplingSystem` → `PlayerIntentBuildSystem` → `MobAISystem` → `CharacterPhysicsSystem` → `MovingBlockSystem` → `PlayerRuntimeUpdateSystem` → `FallDamageSystem` → `ViewBobSystem` |
| 方块交互与战斗 | `BlockTargetSystem`（选块）→ `PlayerMeleeSystem` → `ProjectileSystem` → `DamageSystem` → `HurtEffectDecaySystem` → `DeathSystem` → `BlockBreakSystem` → `SoilTillingSystem` → `BucketUseSystem` → `BlockPlaceSystem` |
| 物品/掉落 | `ItemSpawnSystem` → `ItemPhysicsSystem` → `ItemMergeSystem` → `ItemPickupSystem` → `ItemLifetimeSystem` |
| 粒子 | `ParticleSpawnSystem` → `ParticleSimulationSystem` → `ParticleCleanupSystem` |
| 生存 | `HungerDepletionSystem` |
| 音频/呈现 | `PlayerFootstepAudioSystem` → `FallRollEffectSystem` → `AudioSyncSystem` → `NetworkInterpolationSystem` |
| 视觉同步 | `SteveSyncSystem` → `SteveAnimationSystem` → `MobAnimationSystem` → `TransformHierarchySystem` |
| 插值 | `FallingBlockInterpolateSystem`（把 20 TPS 的移动平滑到 60Hz） |

**修改顺序的注意点**：加新系统时先想清楚它消费谁的数据、谁消费它的数据，插在对应位置。系统注册还支持 `FixedUpdateDebugCategory`（State/Drop/Particle，影响 Dashboard 计时归类）与 `PostSystemHook`（目前只有 `AfterDamageSystem`，供渲染侧在伤害后同步状态）。

### 4.3 Server profile 的差异

`buildServerFixedUpdateSystems`（`GameplayPipeline.cpp:126`）：**没有**客户端专属的输入采样、方块交互、粒子/音频、视觉同步系统——服务器只跑权威玩法系统（AI、物理、战斗、物品）。因为 `GameplayScene` 在服务器进程中也存在（`dedicated_server` 场景），Pipeline profile 在构造时指定。

## 5. tick 流水线（20 TPS 权威模拟）

由 `GameFrameOrchestrator::runFixedUpdate` 末尾的 tickClock 驱动（`GameFrameOrchestrator.cpp:198`）：

```
session.gameplayScene().tickClock().advance(scaledFixedStep);
while (tickClock().shouldTick() && ticksThisFrame < tickClock().maxTicksPerFrame()) {
    session.gameplayScene().runOneTick();
    tickClock().consumeTick();
}
```

`runOneTick` 执行 `GameplayPipeline::runOneTick` 的 tick 系统链（Client profile，`GameplayPipeline.cpp:143`）：

| 系统 | 职责 |
| --- | --- |
| `FluidTickSystem` | 水流扩散的计划方块刻 |
| `FarmlandMoistureSystem` | 耕地湿润状态 |
| `RandomTickSystem` | 方块随机刻（作物生长、菌丝扩散…） |
| `BlockSupportSystem` | 支撑检查，悬空方块 → 事件 → 坠落方块 |
| `PressurePlateSystem` | 压力板状态 |
| `RedstoneSystem` | 红石更新队列处理 |
| `RedstoneDeviceActionSystem` | 红石元件动作（活塞、门…） |
| `HopperSystem` | 漏斗物品转移 |
| `FallingBlockSpawnSystem` / `FallingBlockTickSystem` | 坠落方块生成与逐格下落 |

> **为什么有两条模拟流水线？** 物理/战斗/物品需要 60Hz 才平滑（按键响应），而方块刻/红石等世界模拟 20Hz 即可且与 Minecraft 语义一致。渲染帧率（可变，如 144Hz）不参与模拟，只做插值。

## 7. renderFrame 流水线

入口：`GameFrameOrchestrator::renderFrame`（`GameFrameOrchestrator.cpp:229`）→ `RenderScene::renderGameplayFrame` → `DeferredPipeline/ForwardPipeline::renderFrame`。

### 7.1 Orchestrator 侧（组装请求）

```
① 多人模式且出生区块未就绪 → 只 receiveMessages，跳过渲染
② PresentationController.beginFrame(window) → 获取 swapchain 帧（PresentationFrame）
③ applyFrameBoundaryNvidiaSettings（NVIDIA 反射/帧生成设置）
④ presentationBuilder().build(reg, cameraController, worldView, alpha)
      —— 从 ECS 一次性收集渲染快照（实体网格、掉落物、粒子、灯光、方块目标…）
⑤ renderScene.setRenderLocalPlayerModel / setHeldBlockLightValue / setEyeInWater
⑥ 组装 RenderGameplayFrameRequest（相机、尺寸、天气、雨雪、手持物、目标方块…）
⑦ renderScene.renderGameplayFrame(request)
⑧ 3D 场景完成后、UI 之前：m_preUiCallback（截图捕获钩子，validation 用）
⑨ HUD（GameplayHudPresenter）+ ImGui 调试面板 → 合成 UI 帧
⑩ PresentationController 提交交换链
```

### 7.2 RenderScene 侧（渲染编排）

入口：`RenderScene::renderGameplayFrame`（`src/renderer/core/RenderScene.cpp:576`），内部调用 `renderFrame`（`:280`）：

```
① prepareFrameResources(frameRenderSize) —— 尺寸/资源检查
② executeFrameBeginGraph() —— 独立小图：GPU 计时器重置
③ m_terrainStreamingService.beginFrame() / m_sceneTlasCache.beginFrame() —— 网格与加速结构准备
④ buildFrameContext() → FrameContext（相机、时域参数、天气、曝光）
⑤ m_activePipeline->renderFrame(ctx, settings)
      —— DeferredPipeline（默认）或 ForwardPipeline 装配并执行完整 RenderGraph
⑥ 返回 FrameOutput（sceneColor / sceneDepth / 时序历史）
```

### 7.3 RenderGraph 执行（DeferredPipeline 概览）

`DeferredPipeline::renderFrame`（`src/renderer/core/DeferredPipeline.cpp:801`）按顺序 addPass，`RenderGraph::execute` 解析依赖、创建转瞬资源并提交：

```
SkyCapture → GBuffer(地形/实体/掉落) → Velocity → Shadow(CSM/PCSS)
→ HiZ → SSAO → ClusteredLighting → DeferredLighting → SSR → ReflectionProbeGrid
→ RtgiTrace → NRD(GuidePrep + 降噪) → SceneComposite → WaterComposite
→ 透明地形 → 粒子 → Volumetric → TemporalResolve(TAA) → MotionBlur → DoF
→ PostProcess(Bloom/Tonemap/Grade) → SceneOutput → DepthOutput
```

每个 pass 的完整定义与自定义 pass 的写法见 **05 篇**。

## 8. 网络消息流（单机与联机）

无论单机还是联机，逻辑都走同一条消息路径——区别只在传输层：

```
单机： GameClient ⇄ InProcessTransport ⇄ GameServer（同进程，shared_ptr 直传）
联机： GameClient ⇄ ENetTransport(UDP) ⇄ GameServer（跨机器）
```

### 8.1 上行（客户端 → 服务器）

1. ECS 的 `PlayerIntentBuildSystem` 把输入快照写成意图组件。
2. `sendClientInput`（`GameFrameOrchestrator.cpp:50`）在 fixedUpdate 末尾把意图打包成 `net::ClientInputPacket` 发送。
3. `GameServer` 的 tick 循环 `receiveMessages` → 解包 → 权威应用（移动、方块交互 `ClientBlockAction`、聊天命令…）。

### 8.2 下行（服务器 → 客户端）

1. `GameServer` tick 中广播：方块变化（批量 + 光照增量）、实体位置、掉落物、生物、抛射物、世界时间/天气、模式、死亡/重生。
2. `Game::updateFrame` → `GameSession::receiveWorldMessages`（`GameSession.cpp:570`）→ `GameClient::receiveMessages` 解包应用到 `ClientWorld` 与 `ClientEntityStore`。
3. fixedUpdate 的 `NetworkInterpolationSystem` 对远端实体做插值。

> `GameSession::updateWorldAroundLocalPlayer`（`GameSession.cpp:560`）在每次服务器 tick 时根据本地玩家位置更新流式加载中心。单机模式下 `GameServer` 与 `GameClient` 之间通过事件/直接调用几乎同步执行，因此单机表现就是"零延迟服务器"。

## 9. 时间系统

`src/engine/platform/Time.h` 是全局静态时钟，贯穿全部流水线：

| API | 含义 |
| --- | --- |
| `Time::beginFrame()` / `getFrameIndex()` | 帧索引（渲染/时序用） |
| `Time::update()` / `getRawDeltaTime()` | 真实时间增量（主循环驱动） |
| `Time::getGameTime()` / `advanceGameTime(dt)` | 游戏世界时间（fixedUpdate 步进，受 `setTimeSpeed` 缩放，暂停时为 0） |
| `Time::getTimeSpeed()` / `setTimeSpeed(v)` | 模拟时间倍率（暂停/慢放用） |

**常见错误**：动画/相机插值应该用 `getGameTime()` 或帧内 alpha，而不是 `getRawDeltaTime()`；渲染侧不要依赖游戏时间推进的假设（渲染频率可变）。

## 10. 关键数据在帧内的传递路径

| 数据 | 生产者 | 传递方式 | 消费者 |
| --- | --- | --- | --- |
| 按键/鼠标 | GLFW → `InputManager` | `InputSnapshot`（值拷贝快照） | 所有 ECS 输入系统、状态机 |
| 玩家意图 | `InputSamplingSystem` | 组件（`MoveIntentComponent` 等） | `PlayerIntentBuildSystem` → 物理/方块交互 |
| 方块目标 | `BlockTargetSystem`（射线检测） | `BlockTargetComponent` | `BlockBreakSystem`、`BlockPlaceSystem`、状态机交互 |
| 服务器权威方块变化 | `GameServer` | 网络包 / InProcess | `ClientWorld` → 渲染 |
| 渲染快照 | `GameplayPresentationBuilder::build` | `GameplayPresentationSnapshot`（值语义） | `RenderScene`（只消费快照，不回查 ECS） |
| 时域参数 | `FrameContext` | `FrameContext`（每帧构造） | 所有 Pass（jitter、帧索引、历史） |
| GPU 计时 | `RenderDebugService` | `GpuFrameStats` / `RenderGraphFrameStats` | Dashboard、验证报告 |

**最重要的设计约束**：`RenderScene` 从不直接读 ECS 或 World——它只依赖 `IWorldView`（只读世界接口）与 `GameplayPresentationSnapshot`。这条边界让渲染可以独立测试、独立后端化。
