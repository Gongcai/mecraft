## 一、总体概述

Mecraft 采用经典的 **客户端-服务器（Client-Server）架构**，并以 **服务器权威（Server-Authoritative）** 模型作为同步核心。系统同时支持两种运行模式：

- **单人模式**：服务器与客户端运行在同一进程内，通过 `InProcessTransport` 进行零拷贝通信。
- **多人模式**：通过 `ENetTransport`（基于 ENet 的 UDP 可靠传输）连接远程专用服务器。

网络系统的核心特征：

- **传输层抽象统一**：通过 `ITransportEndpoint` 接口将进程内通信与真实网络通信统一，上层逻辑对底层传输完全无感知。
- **类型擦除数据包**：采用统一 `Packet` 结构体 + `MessageType` 枚举 + `std::any` 类型擦除，无虚函数继承体系。
- **四通道可靠性分级**：控制 / 世界 / 状态 / 聊天 四个通道分别映射 ENet 的可靠/不可靠语义，高频数据走不可靠通道降低延迟。
- **服务器权威 + 轻量客户端预测**：服务器拥有世界、玩家、实体的权威状态，客户端本地模拟玩家操作并接收服务器快照校正。
- **快照缓冲插值**：远程实体使用 8 帧环形缓冲区做插值平滑，延迟 2 个 Tick 渲染。
- **RLE 区块压缩**：区块数据按 SubChunk 分段进行 Run-Length Encoding，显著减少网络传输量。
- **版本兼容解码**：多个解码器支持历史消息格式，实现协议平滑升级。
- **无独立网络线程**：网络 I/O 完全集成在游戏主循环中同步轮询，简化线程模型。

## 三、传输层设计（Transport）

### 3.1 抽象接口 `ITransportEndpoint`

**文件**：`src/net/Transport.h`

这是整个网络系统的核心抽象，采用 **策略模式** 解耦传输实现与上层逻辑：

```cpp
class ITransportEndpoint {
public:
    virtual ~ITransportEndpoint() = default;
    virtual void send(Packet packet) = 0;          // 发送数据包
    virtual bool tryReceive(Packet& out) = 0;       // 非阻塞接收
    virtual bool isConnected() const { return true; }
    virtual bool hasActiveRemote() const { return isConnected(); }
};
```

关键设计点：
- `send()` 接受值语义 `Packet`，内部可移动语义优化。
- `tryReceive()` 为非阻塞接口，无消息时返回 `false`。
- `isConnected()` / `hasActiveRemote()` 用于连接状态检测与断线清理。

`GameClient` 和 `GameServer` 仅依赖此接口，不关心底层是进程内队列还是 UDP 套接字。

### 3.2 进程内传输 `InProcessTransport`

**文件**：`src/net/InProcessTransport.h` / `src/net/InProcessTransport.cpp`

用于单人模式，服务器与客户端同进程运行时的零拷贝传输。

**工厂方法**：
```cpp
static std::pair<std::unique_ptr<ITransportEndpoint>, std::unique_ptr<ITransportEndpoint>> createPair();
```

创建一对配对端点，共享一个 `std::shared_ptr<std::mutex>` 和两个 inbox 队列：
- 端点 A 发送 → 推入端点 B 的 inbox
- 端点 B 发送 → 推入端点 A 的 inbox

**零拷贝机制**：`Packet` 结构体包含 `std::any inProcessPayload` 字段，可直接携带 C++ 对象（如 `std::shared_ptr<Chunk>`），完全跳过序列化/反序列化开销。

**线程安全**：所有队列操作通过共享互斥锁保护，支持跨线程调用。

### 3.3 ENet 网络传输 `ENetTransport`

**文件**：`src/net/ENetTransport.h` / `src/net/ENetTransport.cpp`

基于 [ENet](http://enet.bespin.org/) 库的 UDP 可靠传输，用于多人模式。

#### 3.3.1 服务器端（Host 模式）

```cpp
bool listen(uint16_t port, size_t maxClients = 32, size_t channelCount = 4);
```

- 绑定到 `in6addr_any`（IPv4 + IPv6 双栈监听）
- 默认最大 32 个客户端，4 个通道
- 内部维护多 Peer 状态：

```cpp
std::unordered_map<ENetPeer*, std::shared_ptr<PeerState>> m_peerStates;
std::queue<std::shared_ptr<PeerState>> m_pendingAccepted;
```

每个 `PeerState` 拥有独立的接收队列和互斥锁，实现多客户端消息隔离。

#### 3.3.2 客户端（Client 模式）

```cpp
bool connect(const std::string& host, uint16_t port, uint32_t timeoutMs = 5000);
```

默认 5 秒连接超时。

#### 3.3.3 发送流程

`send()` 方法（`ENetTransport.cpp` 第 157-199 行）：

```
1. encodeTypedPayload(packet)      -- 将 inProcessPayload 编码为 payload 二进制
2. PacketCodec::encode(packet)     -- 加上 6 字节头部
3. mapChannel(packet.channel)      -- 映射到 ENet 通道和可靠性标志
4. enet_packet_create()            -- 创建 ENet 包
5. enet_peer_send() / enet_host_broadcast()  -- 发送
6. enet_host_flush()               -- 刷新
```

#### 3.3.4 接收流程

`poll()` → `tryReceive()`（`ENetTransport.cpp` 第 239-481 行）：

```
1. poll() 调用 enet_host_service(host, &event, 0)  -- 非阻塞，超时=0
2. ENET_EVENT_TYPE_RECEIVE 事件:
   a. PacketCodec::decode()  -- 解码 6 字节头部，提取 channel/type/payload
   b. 根据 packet.type (MessageType) switch 分发:
      - 调用对应的 PacketCodec::decodeXxx() 解码 payload
      - 将结果存入 packet.inProcessPayload (std::any)
   c. 推入接收队列 (m_receiveQueue 或 peerState->receiveQueue)
3. tryReceive() 从队列中弹出已解码的 Packet
```

#### 3.3.5 通道映射

`mapChannel()` 方法（`ENetTransport.cpp` 第 663-676 行）：

| PacketChannel | ENet Channel | ENet Flags | 可靠性 |
|--------------|-------------|------------|--------|
| `ReliableControl` (0) | 0 | `ENET_PACKET_FLAG_RELIABLE` | 可靠有序 |
| `ReliableWorld` (1) | 1 | `ENET_PACKET_FLAG_RELIABLE` | 可靠有序 |
| `UnreliableState` (2) | 2 | 0 | 不可靠无序 |
| `ReliableChat` (3) | 3 | `ENET_PACKET_FLAG_RELIABLE` | 可靠有序 |

#### 3.3.6 编码分发器 `encodeTypedPayload()`

`ENetTransport.cpp` 第 559-661 行，一个大型 switch 语句，根据 `packet.type` 调用对应的 `PacketCodec::encodeXxx()` 函数，将 `inProcessPayload`（`std::any`）转换为 `payload`（`vector<uint8_t>`）。这是发送时的"序列化分发"。

接收时的"反序列化分发"则在 `poll()` 的 `ENET_EVENT_TYPE_RECEIVE` 处理中，同样是 switch 语句。

#### 3.3.7 多客户端广播

服务器端 `send()` 在没有特定 `PeerState` 时使用 `enet_host_broadcast` 广播给所有客户端。

## 四、协议层（Protocol）

### 4.1 Packet 结构体

**文件**：`src/net/Protocol.h` 第 78-83 行

```cpp
struct Packet {
    PacketChannel channel = PacketChannel::ReliableControl;
    MessageType type = MessageType::ClientHello;
    std::vector<uint8_t> payload;           // 二进制载荷（网络传输用）
    std::any inProcessPayload;              // 零拷贝载荷（进程内传输用）
};
```

**设计特点**：未采用面向对象的 Packet 继承体系，而是使用统一结构体 + 枚举区分类型 + `std::any` 类型擦除。这是典型的 **类型擦除（type-erased）** 设计，避免了虚函数开销，同时支持双路径传输。

### 5.2 底层序列化原语

**文件**：`src/net/PacketCodec.h` 第 855-912 行

所有基本类型读写使用 **小端序（Little-Endian）**：

| 写入函数 | 读取函数 | 大小 | 说明 |
|---------|---------|------|------|
| `pushU8` | `readU8` | 1 字节 | 无符号 8 位 |
| `pushU16` | `readU16` | 2 字节 | 无符号 16 位 |
| `pushI32` / `pushU32` | `readI32` / `readU32` | 4 字节 | 有/无符号 32 位 |
| `pushFloat` | `readFloat` | 4 字节 | IEEE 754 单精度（通过 `memcpy` 转换） |
| `pushString` | `readString` | 4+N 字节 | 4 字节长度前缀 + 原始字节 |

### 5.3 RLE 压缩（区块数据专用）

**文件**：`src/net/PacketCodec.h` 第 793-853 行

- `encodeRleU16` / `decodeRleU16`：16 位值的 Run-Length Encoding，用于方块 ID 数组
- `encodeRleU8` / `decodeRleU8`：8 位值的 Run-Length Encoding，用于光照数据数组
- 区块编码标记：`kChunkEncodingRleSubChunks = 1`
- 区块数据按 SubChunk（16×16×16）分段独立 RLE 压缩
- 每段检测是否有显式光照数据（与隐式光照对比，一致则不编码）

### 5.4 协议版本兼容性

多个解码器实现了 **向后兼容** 逻辑，通过 payload 大小判断版本：

| 解码器 | 支持的格式 |
|--------|-----------|
| `decodeServerSnapshot` (479) | 新增 health/respawned/dead 字段为可选 |

### 6.2 服务器 Tick 循环

**文件**：`src/server/GameServer.cpp` 第 685-743 行（`tick()` 方法）

每 Tick（1/20 秒）执行 14 个阶段，严格有序：

```
 1. processClientMessages()              -- 接收并处理所有客户端消息
 2. cleanupDisconnectedClients()         -- 清理断开连接的客户端
 3. tickWorldSystems()                   -- 流体系统 Tick + 方块支撑规则
 4. 自动存档检查（每 300 秒）
 5. m_world.update(loadCenter, dt)       -- 世界流式加载/卸载、光照刷新
 6. tickServerEcs(dt)                    -- 服务器端 ECS 固定更新
 7. updatePlayerLifecycle(dt)            -- 玩家生命周期（伤害/死亡/重生）
 8. sendNewChunksToClients()             -- 发送新区块
 9. sendSnapshotsToClients()             -- 发送权威位置/速度/血量快照
10. sendInventorySnapshotsToClients()    -- 发送物品栏（仅有变化时）
11. syncEntitiesToClients()              -- 实体生成/销毁/快照同步
12. syncPlayersToClients()               -- 多人玩家互相同步
13. sendBlockUpdatesToClients()          -- 发送方块更新批量包
14. ++m_currentTick                      -- 递增 Tick 计数器
```

**顺序设计原则**：
- 先处理输入（阶段 1），再更新世界状态（阶段 3-7），最后发送同步数据（阶段 8-13）
- 确保客户端收到的快照反映的是本 Tick 处理后的最新状态

## 十、区块同步机制

### 10.1 ChunkTicketManager（区块票据管理器）

**文件**：`src/server/ChunkTicketManager.h`

多级票据系统，管理区块加载优先级：

| 票据类型 | 用途 |
|---------|------|
| `Spawn` | 世界出生区域，始终加载 |
| `PlayerSimulation` | 玩家模拟半径（实体/流体/随机 Tick） |
| `PlayerView` | 玩家视野距离（加载并发送给客户端） |
| `Forced` | 命令/调试强制加载 |

三级半径关系：
```
simulationRadius < viewRadius < loadRadius(viewRadius+1) < unloadRadius(viewRadius+3)
```

带滞后设计避免边界区块反复加载/卸载抖动。

### 10.2 区块发送策略

**文件**：`src/server/GameServer.cpp` 第 1300-1364 行（`sendNewChunksToClients()`）

核心逻辑：
1. 每个客户端维护独立的 `ChunkTicketManager`，根据客户端 `viewDistance` 和玩家位置计算需要加载的区块
2. 初始区块激进发送：前 81 个区块每 tick 最多发 96 个；之后每 tick 最多 24 个
3. 通过 `client.sentChunks` 集合跟踪已发送区块，避免重复发送
4. 超出卸载半径的区块发送 `ChunkUnload` 消息

### 10.3 区块数据传输

```cpp
void GameServer::sendChunkDataToClient(ConnectedClient& client, int cx, int cz)
```

- 通道：`ReliableWorld`（必须完整到达）
- 进程内模式：`ChunkDataMessage.chunk` 直接共享 `shared_ptr<Chunk>`（零拷贝）
- 网络模式：通过 `PacketCodec::encodeChunkData` 进行 RLE 编码

### 10.4 区块序列化编码

`PacketCodec::encodeChunkData` / `decodeChunkData`：

- 编码标识 `kChunkEncodingRleSubChunks = 1`
- 按 SubChunk（16×16×16）分块编码
- 每块检测是否有显式光照数据（与隐式光照对比，一致则不编码以节省空间）
- 方块 ID 使用 RLE-U16 编码，光照使用 RLE-U8 编码
- 解码后重建 HeightMap 并标记所有 SubChunk 为脏

### 10.5 出生区块就绪检测

- 服务器端：`checkSpawnChunksReady()` 检查 5×5 出生区域是否加载完成
- 客户端端：`GameClient::kSpawnChunksThreshold = 25`（5×5），收到足够区块后设置 `m_spawnChunksReady = true`
- 在区块未就绪前，玩家不发送输入，物理模拟不启动

### 11.3 实体同步流程（服务器端）

**文件**：`src/server/GameServer.cpp` 第 1943-2142 行（`syncEntitiesToClients()`）

每个服务器 Tick 执行 5 步：

4. **发送 Spawn 消息**：对每个客户端，为其尚未收到的已同步实体发送 `EntitySpawn`（通道：`ReliableWorld`）
5. **发送快照**：构建包含所有已同步实体的 `EntitySnapshotMessage`（位置、速度、朝向、生命值、受伤标志），通过 `UnreliableState` 通道发送

| `handleImpact(const EntityImpactMessage&)` | EntityImpact | 触发碰撞粒子效果 |
| `handleSnapshot(const EntitySnapshotMessage&)` | EntitySnapshot | 批量更新实体位置/速度/朝向/血量 |

### 11.7 本地权威实体识别

`ClientEntityStore::isLocallyAuthoritative()` 检查实体是否为本地权威。本地玩家的实体在 `handleSpawn` 中通过 `findExistingEntity()` 匹配已存在的本地实体，标记为 `m_locallyAuthoritativeNetIds`。这些实体在 `handleSnapshot` 中 **跳过** 快照插值，完全由本地物理驱动。

## 十五、客户端预测与服务器校正

### 15.1 架构特点

Mecraft 采用 **轻量级客户端预测 + 服务器权威校正** 模式，而非完整的回滚重演（rollback/replay）：

1. **客户端本地模拟**：客户端在本地运行完整的 ECS FixedUpdate Pipeline（物理、移动、交互等），玩家操作即时反馈
2. **输入上报**：每个 FixedUpdate 帧将本地玩家状态（位置、速度、朝向、输入）发送给服务器
3. **服务器权威**：服务器接收输入后更新 `client.lastPosition/lastVelocity`，然后通过 `ServerSnapshot` 回传权威位置
4. **校正方式**：客户端在 `handleServerSnapshot()` 中接收权威位置，存储在 `m_authPosition` 和 `m_lastSnapshot` 中

### 15.2 玩家状态校正

**文件**：`src/client/GameClient.cpp` 第 307-344 行（`handleServerSnapshot`）

- 接收 `ServerSnapshot`，更新 `m_authPosition` 和 `m_lastSnapshot`
- 更新 ECS 中的 `HealthComponent`
- 仅在 `playerRespawned` 标志为 true 时直接重置玩家位置和速度到权威值
- 伤害标志上升时触发受伤效果

**关键点**：当前实现 **不会** 在每帧强制将客户端位置校正到服务器位置。客户端位置由本地物理系统驱动，服务器快照用于：
- 出生/重生时强制对齐
- 生命值/死亡状态同步
- 作为 `getAuthoritativePosition()` 的来源供其他系统参考

### 15.3 输入序列号确认

- 客户端每次发送输入递增 `m_inputSequence`
- 服务器回传 `ackInputSequence`（确认的输入序列号）
- 这为未来实现完整的回滚重演预留了接口，但当前未使用输入缓冲区重放

### 15.4 实体快照插值系统

**文件**：`src/ecs/systems/network/NetworkInterpolationSystem.cpp`

这是 **最完善的客户端预测/校正机制**，但应用于远程实体（非本地玩家）。

#### NetworkInterpolationComponent 参数

```cpp
static constexpr std::size_t SnapshotBufferSize = 8;   // 快照环形缓冲区
float positionLerpSpeed = 12.0f;        // 位置插值速度
float rotationLerpSpeed = 16.0f;        // 旋转插值速度
float snapDistance = 8.0f;              // 超过此距离直接瞬移
float serverTickRate = 20.0f;           // 服务器 Tick 速率
float interpolationDelayTicks = 2.0f;   // 插值延迟（Tick 数）
float renderServerTick = 0.0f;          // 当前渲染的服务器 Tick
```

#### 插值策略

1. **快照缓冲区采样**（`sampleSnapshotBuffer`）：
   - 维护最多 8 个快照样本的有序缓冲区
   - 计算延迟渲染 Tick = `newestTick - interpolationDelayTicks`
   - 渲染 Tick 以 `serverTickRate * dt` 速率前进，但不超过延迟后的最新 Tick
   - 在两个相邻快照之间线性插值

2. **瞬移保护**：如果两个快照间距离超过 `snapDistance`，不插值，直接使用旧位置

3. **回退平滑**（`applyFallbackTarget`）：
   - 当快照不足 2 个时使用指数平滑
   - 距离超过 `snapDistance` 直接瞬移
   - 否则使用 `1 - exp(-speed * dt)` 的指数平滑因子

4. **角度插值**：使用最短角度差插值（`shortestDeltaDegrees` / `shortestDeltaRadians`），避免旋转绕远路

5. **旋转平滑**：使用指数平滑（`smoothingAlpha = 1 - exp(-speed * dt)`）

## 十六、状态一致性保障

### 16.1 可靠性策略

| 数据类型 | 通道 | 可靠性 | 策略说明 |
|----------|------|--------|---------|
| 握手/登录 | ReliableControl | 可靠有序 | 必须到达且有序 |
| 区块数据 | ReliableWorld | 可靠有序 | 必须完整到达 |
| 方块更新 | ReliableWorld | 可靠有序 | 必须到达，避免状态分歧 |
| 实体 Spawn/Despawn | ReliableWorld | 可靠有序 | 生命周期事件不能丢失 |
| 实体快照 | UnreliableState | 不可靠 | 高频数据，丢包可接受（下个快照补偿） |
| 玩家输入 | UnreliableState | 不可靠 | 高频，最新输入最重要 |
| 玩家状态快照 | UnreliableState | 不可靠 | 权威位置，丢包等下一个 |
| 物品栏 | ReliableWorld | 可靠有序 | 必须准确，仅变化时发送 |
| 聊天/命令 | ReliableChat | 可靠有序 | 必须到达且有序 |

### 16.2 物品栏差量同步

`sendInventorySnapshotsToClients()` 只在物品栏实际变化时发送（与上次快照对比），避免不必要的网络流量。

### 16.3 断线重连与清理

- `cleanupDisconnectedClients()` 检测 `isConnected()` 和 `hasActiveRemote()`
- 断线时广播 `EntityDespawn` 通知其他玩家
- 清理所有客户端状态（已发送区块、已生成实体等）

### 16.4 进程内模式优化

在单人模式下，`InProcessTransport` 通过配对的线程安全队列直接传递 `Packet` 对象，`inProcessPayload` 字段使用 `std::any` 携带原始 C++ 对象（如 `shared_ptr<Chunk>`），实现零拷贝传输，避免了序列化/反序列化开销。

### 16.5 版本兼容

多个解码器支持历史消息格式（通过 payload 大小判断版本），实现协议平滑升级，保证客户端/服务器版本不一致时的兼容性。

## 十七、网络线程模型

### 17.1 单线程同步模型

Mecraft **没有独立的网络线程**。网络 I/O 完全集成在游戏主循环中：

```
GameManager::run() {
    while (!window.shouldClose()) {
        window.pollEvents();
        Time::update();
        appStateMachine.update(frameTime, accumulator);  // -> GameSession -> Server::tick + Client::receiveMessages
        appStateMachine.render(frameTime);
    }
}
```

- **服务器**：`GameSession::updateWorldAroundLocalPlayer()` 调用 `m_server->tick(dt)`，在 tick 内调用 `processClientMessages()` 和各种 `send*ToClients()`
- **客户端**：`GameSession::updateWorldAroundLocalPlayer()` 调用 `m_client->receiveMessages()`
- **ENet 轮询**：`ENetTransport::poll()` 使用 `enet_host_service(host, &event, 0)`（超时为 0，非阻塞）处理所有待处理事件

### 17.2 线程安全

| 组件 | 线程安全机制 |
|------|-------------|
| `InProcessTransport` | `std::shared_ptr<std::mutex>` 保护共享队列 |
| `ENetTransport` 接收队列 | `std::mutex` 保护 `m_receiveQueue` |
| `ENetTransport` PeerState | 每个 `PeerState` 独立互斥锁保护 `receiveQueue` |
| `ENetTransport::send()` | 非线程安全（假设在主线程调用） |
| `ClientWorld` | `std::mutex` 保护区块映射 |

### 17.3 Tick 速率

- 服务器逻辑：固定 20 TPS
- `NetworkInterpolationComponent::serverTickRate = 20.0f`
- 客户端输入采样以固定频率发送

## 二十、架构特点总结

### 20.1 设计优势

1. **分层清晰**：Transport 抽象 → Protocol 定义 → Codec 编解码 → Application 逻辑，职责分明。
2. **双模式统一**：单人/多人通过同一 `ITransportEndpoint` 接口统一，上层完全无感知。
3. **零拷贝优化**：进程内传输使用 `std::any` 直接传递 C++ 对象，避免序列化开销，单人模式性能等同于本地调用。
4. **通道优先级**：4 个 ENet 通道按消息重要性分配可靠性，高频数据用不可靠通道减少延迟。
5. **权威服务器模型**：Server 拥有世界权威状态，Client 发送输入并接收快照，防止作弊。
6. **快照缓冲插值**：远程实体使用 8 帧环形缓冲区做插值平滑，延迟 2 个 Tick 渲染，视觉流畅。
7. **RLE 区块压缩**：区块数据按 SubChunk 分段 RLE 压缩，显著减少网络传输量。
8. **版本兼容解码**：Codec 支持多种历史消息格式，保证协议平滑升级。
9. **无独立网络线程**：网络 I/O 在主线程同步轮询，简化线程安全模型，避免多线程同步复杂度。
10. **类型擦除数据包**：统一 `Packet` 结构体 + `std::any`，无虚函数继承体系，性能与灵活性兼得。

### 20.2 架构权衡

| 设计选择 | 优势 | 代价 |
|---------|------|------|
| 无独立网络线程 | 线程模型简单，无需跨线程同步 | 高延迟环境下主线程可能阻塞在 I/O |
| 轻量客户端预测（非回滚重演） | 实现简单，CPU 开销低 | 高延迟下位置分歧无法自动校正 |
| 服务器权威（非客户端权威） | 防作弊，状态一致 | 服务器计算压力大 |
| 静态消息类型（非动态注册表） | 编译时类型安全，无运行时开销 | 新增消息需修改枚举和 switch |
| 单线程 ENet 轮询 | 简化线程安全 | 吞吐量受限于主线程帧率 |
