# 时域、输出与性能

## 1. 目标

RTGI、透明、反射和动态分辨率都依赖可靠的跨帧数据。现代画面不能把 TAA、NRD、超分、
Frame Generation 和曝光分别维护成互不一致的矩阵与速度约定。本章扩充现有
`TemporalFrameContract`，建立统一历史注册、GPU 时间控制闭环、HDR 色彩管理与可执行
性能预算。

## 2. 统一时域帧契约

### 2.1 坐标约定

现有 Mecraft 约定保持不变：

- Velocity 存储 `currentTextureUv - previousTextureUv`。
- Velocity 使用归一化纹理 UV。
- 原生纹理 UV 的正 Y 指向下方。
- Jitter 同时保存 Pixel 与 Projection 表达。
- 当前/上一帧矩阵同时提供 Jittered 与 Non-jittered 版本。

每个 SDK Bridge 在自身边界转换符号、单位、Y 方向和 Jitter。公共 Velocity Texture 不为
某个 SDK 改写。FSR、DLSS 和 NRD 均拥有针对平移、旋转、动态物体的契约测试。

### 2.2 Extent

帧契约拆分：

- `resourceExtent`：按当前质量档最大尺寸分配的历史/工作资源尺寸。
- `renderExtent`：本帧实际渲染矩形。
- `signalExtent`：RTGI/Reflection 等信号实际尺寸。
- `outputExtent`：展示分辨率。
- `renderRect/signalRect`：资源内有效区域与 Origin。

动态分辨率只改变 Active Rect，避免每个微小尺寸变化都销毁 NRD 与时域资源。Bridge 使用
SDK 公开的 Resource Size/Rect Size 字段。Resource Extent、坐标原点、深度约定或不兼容
模式变化才触发资源重建。

现有 `requiresTemporalReset()` 需要从“任意 Render Extent 变化即清空”扩充为按消费者判定：
TAA、FSR、DLSS、NRD、SSR、Volumetric 各自声明能否在固定资源尺寸内接受 Active Rect
变化。

### 2.3 完整运动矢量

| 几何/效果 | Velocity 来源 | 历史身份 |
| --- | --- | --- |
| 静态区块 | 当前/上一帧 View-Projection | Stable Chunk/SubChunk ID |
| 移动方块/刚体模型 | Current/Previous World Transform | Stable Object ID |
| 蒙皮/Morph | Current/Previous Deformed Position | Stable Object ID + Primitive ID |
| 水面 | Transform + Current/Previous Wave Phase | Stable Water Surface ID |
| 透明模型 | Current/Previous World/Deformed Position | PPLL Stable Object ID |
| 粒子 | Current/Previous Particle Position | Stable Particle ID |
| 程序植被 | Current/Previous Wind Deformation | Stable Geometry ID |
| 天空 | 相机旋转重投影 | Sky Class ID |

无效速度使用契约定义的 Sentinel，并生成 Disocclusion Mask。生成错误的零速度会积累旧
表面，因此不能把零向量作为未知速度的表示。

公共 `GVelocity` 保持供 TAA/FSR/DLSS 使用的 RG16F 2D 约定。`NrdMotionPreparation` 从
深度、当前/上一帧变换和公共速度生成 NRD 的 `previous - current` XY 与
`previousViewZ - currentViewZ` Z 分量，形成 2.5D Screen-space Motion 输入。

当前实现将该独立 NRD Motion 固定为 `RGBA16F`，使用当前/上一帧 Non-jittered Inverse Projection
和双帧 Depth 重建正 View-Z；FrameContext 与 TemporalFrameInput 同时保存当前/上一帧 Pre-exposure。
RTGI Raw 在写入有限精度 HDR 前乘当前值，Signal Pack 进入 NRD 前除去当前值，Deferred Lighting
消费 NRD 输出时恢复当前值，NRD 历史不累积曝光变化。全局 Temporal Reset 时禁用上一帧深度并写零
Z Motion。当前全局 producer 显式为 `1`，公共 `GVelocity` 的格式和 `current - previous` 方向不受影响。

### 2.4 历史注册表

新增 `TemporalHistoryRegistry`，由稳定名称登记：

- 所有者与资源代际。
- Resource/Active Extent。
- 当前/上一帧 Texture Handle。
- Reset Reasons Bitmask。
- Last Valid Frame 与 Last Submission Token。

统一 Reset Reasons：First Frame、Camera Cut、Teleport、World Reload、World Origin Shift、
Resource Extent、Pipeline Mode、Method、Projection、Frame Discontinuity、Asset Revision。
Dashboard 能展开查看每项历史的最近失效原因。

## 3. 帧内顺序

```text
Render-resolution Depth/GBuffer/Velocity
        │
        ├── Direct Lighting / RTGI / NRD / Reflection
        ├── Atmosphere / Volumetrics / Opaque Composite
        └── Multi-layer Transparency
        │
        ▼
Render-resolution Pre-exposed HDR Scene
        │
        ├── Native TAA
        ├── FSR 3.1 Upscaling
        └── DLSS Super Resolution
        │
        ▼
Output-resolution Linear HDR Scene
        │
        ├── Bloom / Exposure / Color Grading
        └── Display Tone Map / Gamut Mapping
        │
        ▼
HUD-less Display Color
        │
        ├── Native Present
        ├── FSR Frame Generation
        └── DLSS Frame Generation
        │
        ▼
UI Composite in target display space
```

NRD 在 Temporal Upscaler 之前运行，因为其 Normal、View-Z、Motion 与 Raw Signal 位于
Render Extent。Frame Generation 只消费完成 Tone Map 的 HUD-less Display Color 和自身
规定的 Motion/Depth/UI 数据，不参与 RTGI 历史步进。

## 4. 动态分辨率闭环

### 4.1 控制目标

当前 Dynamic Resolution 仅把布尔值传给 SDK，缺少根据 GPU 时间修改 Render Extent 的
控制器。新增 `DynamicResolutionController`：

- 输入是真实渲染帧 GPU Timestamp，不使用生成帧展示间隔。
- 目标时间由 60/90/120 FPS 设置换算，并预留 Present/系统抖动余量。
- 使用 EMA 与 p95 Window 抑制单帧尖峰。
- Scale 有公开的 Min/Max，尺寸按 SDK 要求对齐到 8/16 Pixels。
- 每帧 Scale 变化率受限，进入目标死区后保持。
- CPU Bound、GPU Bound、VSync Bound 和 Frame Generation 状态分别显示。

控制器只修改 Render Extent。RTGI Method、Ray Distance、NRD Method、透明层数、阴影
算法和材质质量不随 GPU 时间改变。

### 4.2 GPU 时间样本

Render Graph 每个大阶段写 Timestamp，并在对应 Submission 完成后读取。控制器使用：

```text
sceneGpuMs = lastSceneTimestamp - firstSceneTimestamp
```

Frame Generation、Present Wait 和 CPU Frame Pacing 不混入该值。Timestamp 缺失或无效时
控制器保持当前 Scale 并报告 `GpuTimingUnavailable`，不根据 CPU 时间猜测。

### 4.3 稳定性测试

- 固定负载 30 秒，Scale 不持续来回振荡。
- 从室内走向复杂森林，Scale 在设定响应时间内收敛。
- Camera Cut 与 Scale 变化期间无未初始化边缘或历史错位。
- FSR/DLSS 的输入 Rect、Jitter Phase 和 Motion Scale 同步变化。
- NRD 使用固定 Resource Extent 与更新后的 Rect Size。

## 5. 曝光与色彩管理

### 5.1 工作色域

Vulkan 现代管线采用线性 ACEScg/AP1 作为统一 HDR 工作色域：

- sRGB 资产纹理解码为 Linear Rec.709，再转换到 AP1。
- 物理天空、灯光、Emissive、Probe、RTGI 和 Bloom 都在 AP1 中计算。
- UI 保持 sRGB 创作，在最终 UI Composite 转换到目标显示空间。
- GBuffer、历史和 SDK Bridge 清楚标记实际色域与 Pre-exposure。

迁移前建立 Macbeth ColorChecker、灰阶、饱和色与 Emissive Nits 测试，防止矩阵重复应用。

### 5.2 Pre-exposure

场景辐射在写入有限精度 HDR Buffer 前乘当前 Pre-exposure。Temporal Frame 同时保存当前
与上一帧 Pre-exposure，历史读取按比值校正。RTGI Raw、NRD 输入输出、SSR、透明与 Bloom
遵循同一规则。

Auto Exposure 使用 Log Luminance Histogram、Percentile 过滤、独立亮/暗适应速度和物理
EV100 范围。相机切换、世界加载与显示模式改变有明确曝光历史策略。

### 5.3 Tone Map

Tone Map 使用固定、可文档化的 ACES 风格显示变换，包含：

- Exposure。
- Scene-referred 到 Display-referred 映射。
- Output Gamut Transform。
- Highlight Desaturation 与 Gamut Compression。
- SDR/HDR 的不同 Display Encoding。

后处理 Debug View 可停在 Linear HDR、Pre-exposed、Tone-mapped、Gamut-mapped 与 Encoded
各阶段，便于定位颜色错误。

## 6. SDR 与 HDR 交换链

### 6.1 显示模式

Vulkan 枚举 Surface Format/Color Space 后提供显式模式：

| 模式 | 推荐格式 | Color Space | 编码 |
| --- | --- | --- | --- |
| SDR | `B8G8R8A8_UNORM` | `SRGB_NONLINEAR` | sRGB |
| HDR10 | `A2B10G10R10_UNORM_PACK32` | `HDR10_ST2084_EXT` | Rec.2020 + PQ |
| scRGB | `R16G16B16A16_SFLOAT` | `EXTENDED_SRGB_LINEAR_EXT` | Linear scRGB |

用户选择的模式不受支持时保持不可选并显示 Surface/OS/Presentation Backend 的具体原因。
交换链创建、DLSS-G/FSR Frame Generation Interop、UI Composite 和截图链都必须声明支持
的格式与 Color Space，任一环节不满足时该组合不可选。

### 6.2 HDR 元数据

HDR10 使用 `VK_EXT_hdr_metadata` 提交显示 Primaries、White Point、Max/Min Luminance、
MaxCLL 与 MaxFALL。设置包含 Paper White 和 Peak Brightness，并在显示模式变化时更新。
截图可输出 Linear EXR 与带色彩元数据的 SDR PNG，二者路径分离。

## 7. 质量模式

Vulkan 现代预设使用可见、可检查的参数组合：

| 项目 | Quality | Performance |
| --- | --- | --- |
| RTGI | Render Extent，1 spp | Checkerboard，1 spp |
| NRD | RELAX_DIFFUSE | REBLUR_DIFFUSE |
| 反射 | SSR + Probe + 可选 RT Reflection | SSR + Probe |
| 多层透明 | PPLL，8 层初始配置 | PPLL，4 层初始配置 |
| 阴影 | CSM + 选定局部灯高采样 | CSM + 选定局部灯低采样 |
| 动态分辨率 | 用户独立开启 | 用户独立开启 |

透明层配置低于场景实际需求时容量检查会报告错误。预设切换会显示完整参数差异并执行
相应历史失效，不在帧中隐藏调整单项算法。

## 8. 参考性能预算

目标硬件为 RTX 4060 Laptop 8GB。首个基准是 1920×1080 Output、Quality Upscaler 对应的
Render Extent、60 FPS、Vulkan Modern Quality、典型体素世界。GPU p95 总时间要求不超过
16.67 ms：

| 阶段 | p95 预算 |
| --- | ---: |
| Scene Upload + GPU Culling + AS Update | 1.30 ms |
| Depth/GBuffer + Sun/Local Shadows | 3.00 ms |
| Cluster + Direct Lighting | 1.30 ms |
| RTGI Trace | 3.00 ms |
| NRD | 2.30 ms |
| Reflection + Atmosphere + Volumetrics | 2.00 ms |
| Multi-layer Transparency | 1.50 ms |
| Temporal Upscale + Bloom + Tone Map + Composite | 1.40 ms |
| 机动余量 | 0.87 ms |

模型基准使用 1000 个实例与指定屏幕 Triangle 数，采用同一 16.67 ms 总预算。单阶段超过
表中预算不直接判定失败，只要总时间、画质和资源预算均达标；表格用于定位工程投入。

普通火把继续作为体素 Point Light 性能与正确性测试入口。测试报告需同时记录火把数量、
视锥覆盖 Cluster 数、Cluster Index 数、`Deferred.Lighting`、局部阴影和总 GPU 时间，并覆盖
动态方块编辑与跨区块光照更新。

610.43.03，使用 `m3_voxel_rtgi_cave`/`m3_model_rtgi_sponza` 场景契约 v2、RELAX_DIFFUSE、

未打点的场景 Overlay/上采样/AS/TLAS 和图间调度间隙；下表保留为接入完整跨度前的历史

移除，`m3_voxel_rtgi_quality` 进入 v3，新的 Render Settings Hash 为

第一轮优化已把 RTGI 与 NRD 聚合时间拆为 `RTGI.Trace`、`RTGI.SignalPack`、`NRD.GuidePrep`、

`complete_gpu_frame_ms`：它使用同一个 `RenderDebugService` 的帧首和终端 GPU timestamp，覆盖
`scene_render_graphs` 的帧首图、主图、场景 Overlay、Temporal Upscale、PostProcess/FSR1，包含图间提交顺序
与 GPU 调度间隙，但不包括 UI 和 Present。该字段同样使用固定 1000 帧窗口输出 `span_ms.p50/p95/p99`；
缺少首尾完整 timestamp、查询仍在进行或终端图失败时 `valid=false`，不会用旧样本填充当前 latest。
2026-08-09 接入 RTGI Counter 遥测后重新采集的 3 帧 RTGI 参考报告已验证该字段：Sponza p95 为
10.768 ms，体素洞穴 p95 为 9.475 ms，均为 3/3 有效样本。该小窗口只验证报告契约和真实 timestamp 链路，不能
替代 1000 帧性能结论。

AS 分项计时随后接入 `acceleration_structure_work`。运行时阶段固定为 `SceneTLAS`、
`TerrainBLAS.Build`、`TerrainBLAS.Compaction`、`AS.DynamicResourcePreparation` 和
`RTGI.SceneTLASBootstrap`，每项发布 CPU/GPU p50/p95/p99、窗口内操作总数，以及单帧 Instance、
Primitive、Scratch 和结构字节峰值；`residency` 发布当前与窗口峰值的 TLAS Instance、唯一 BLAS、
TLAS/BLAS 字节和 Terrain Primitive。`static_blas` 单独标记 `scope=asset_load`，聚合唯一资产的
Build/Compaction CPU/GPU 时间、Primitive、Scratch 与压缩前后字节。`scene_tlas_generations` 分列
Allocation/Reuse/Reuse Wait/Retired Generation，`dynamic_blas` 发布 RigidReuse/Update/Rebuild 及两组
Reject Reason，`terrain_geometry_buckets` 发布 Opaque/Cutout 的当前值、窗口构建总量和峰值。bootstrap
包含内部 SceneTLAS，因此只作为诊断项发布，不重复计入 `total_tracked`。

重新采集的 3 帧报告验证了真实数据链路：Sponza 为 1 个 TLAS Instance、1 个唯一 BLAS 和 18,176 B
引用 BLAS；体素洞穴为 256 个 TLAS Instance、255 个 Terrain BLAS、203,188 个 Terrain Primitive 和
5,397,760 B Terrain BLAS。体素 Primitive 进一步拆为 202,312 个 Opaque 与 876 个 Cutout；Sponza 和场景
内 Static BLAS 的 Cutout Primitive 都为 0。最新窗口中体素 TLAS Allocation 为 0，Sponza 为 1，两个场景
的 Reuse 与 Reuse Wait 都为 0。采样发生在 300 帧预热之后，稳态窗口没有发生地形重建时，Build、
Compaction 和 bootstrap 的操作数与时间为零是准确结果；Static BLAS 的资产加载统计与驻留快照仍保留。
动态编辑、高速流送和首次 bootstrap 的成本需要使用专用 Camera Path/操作脚本重新采集，不能从稳态零值
推断。

RTGI Validation Image 的 Counter Contract v2 已增加独立 GPU 归约和三槽异步读回，Benchmark JSON 的
`rtgi_trace_counters` 发布固定窗口样本数、总像素、Candidate/Confirmed 总量、确认率、每像素峰值、
Sky/Translucent/Miss/Hit/NonFinite 五类 64 位像素计数及最新来源帧。解码器要求五类总和严格等于完整像素数。
Sponza 和体素洞穴的历史 3/3 报告每份总计 2,764,800 像素，Candidate、Confirmed 和峰值均为 0，
这与各自镜头内容一致。V03 Forest Cutout 以相同口径产生 2,142,695 Candidate 与 1,636,266 Confirmed，

该 3 帧窗口只锁定真实 Counter 压力与报告契约，不能当作正式性能结论。非零读回路径同时由生产
`RtgiTracePass` Vulkan Smoke 覆盖。M03 的最新 320×180、1+2 Vulkan smoke 共统计 `115200` 个 Hit，
Sky/Translucent/Miss/NonFinite 均为 `0`，把当前质量定位从射线命中与非法数据轴收敛到命中后的能量采样轴。
Terrain OMM 生产链和独立 `terrain_opacity_micromaps` 报告已接入，后者发布
模式、Alpha/Profile Hash、Four-state subdivision、活动数量/字节、Build Input/Storage/Scratch 字节和三类
microtriangle 计数。真实 Vulkan 已验证 Candidate 模式零 Micromap、OMM 仅关联 Cutout Geometry、压缩与 TLAS

现已完成，两组均为 300 帧预热加 1000 帧有效采样：`RTGI.Trace` p95 从 3.759872 ms 降至 2.804736 ms，
Complete GPU Span p95 从 17.859584 ms 降至 16.940544 ms，Candidate 总量从 716,114,823 降至
128,248,955；RHI 内存增加 613,888 B。OMM 常驻 52 个资源、598,144 B，Opaque/Transparent/Unknown
microtriangle 分别为 1,145,448/510,754/116,854，总数精确等于 `6,926 × 256`。
验证入口使用 `--validation-rtgi-cutout-traversal candidate_loop|opacity_micromap` 显式选择实现轴；该轴不进入锁定
画质 Profile 的 Content Hash，报告在 `render_settings.rtgi_cutout_traversal` 和
`acceleration_structure_work.terrain_opacity_micromaps.mode` 双重记录实际模式，确保两组仍共享同一质量 Profile。

## 9. 性能方法

### 9.1 Capture 规则

- Release 或 RelWithDebInfo，关闭会影响时间的 GPU Debug Validation。
- 固定驱动、电源模式、GPU Clock 状态、输出分辨率和画质设置。
- 预热 300 帧，采集至少 1000 个真实渲染帧。
- 报告 p50、p95、p99，不只报告平均值。
- Frame Generation 的展示 FPS 与真实 GPU Frame Time 分开。
- 体素和模型场景使用版本化 Camera Path 与 World/Asset Hash。

### 9.2 工具

- RHI Timestamp 与 Dashboard 用于持续回归。
- RenderDoc 验证资源、Barrier、Descriptor 与帧结果。
- NVIDIA Nsight Graphics 验证 Ray Query、AS Build、Shader Occupancy 与内存。
- Vulkan Validation Layer 用于开发构建的同步与生命周期检查。

Async Compute 只在 Nsight 时间线证明可与 Graphics 重叠且 Queue Ownership 成本可控后启用。
每次调整保留前后 Capture，禁止凭单帧 FPS 判断收益。

## 10. 自动化与完成标准

自动测试至少覆盖：

- Motion Convention 的 CPU 数学测试与 GPU Pattern Test。
- 各 Reset Reason 对各 History Owner 的作用。
- Active Rect 变化时边界清理与 SDK 参数。
- Dynamic Resolution Controller 的收敛、死区和上下限。
- SDR/HDR Format、Color Space 与 Tone Map Reference Pixel。
- Current/Previous Pre-exposure 比例。
- Frame Generation 开关期间真实 Frame Index 连续。
- GPU Timestamp 缺失的结构化状态。

完成条件：体素与模型 Camera Path 的画质、p95 GPU/CPU 时间、显存、历史稳定性都进入
持续集成报告；动态分辨率保持目标时间且不改变用户选择的渲染算法；HDR 输出通过实际
HDR 显示器与截图数值验证。
